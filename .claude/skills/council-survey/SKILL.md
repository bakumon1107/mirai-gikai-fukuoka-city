# 自治体議会サイト 適合度調査

地方議会のサイトは自治体ごとに公開範囲も形式もまったく違う。
このスキルは、ある自治体で**みらい議会のどの機能まで作れるか**を調べ、
着手判断に使えるレポートを出す。

```
/council-survey <自治体名>
/council-survey <自治体名> <議会サイトのURL>
```

---

## 大原則：推測で埋めない

**このスキルで最も避けたい失敗は、確認していない項目を「ありそう」で埋めること。**
議会サイトは見た目が似ていても中身の粒度がまったく違う。判定を誤ると、
着手してから「会派別賛否が取れない」と分かって手戻りする。

- すべての判定に **根拠URL** を付ける。URLを示せない判定は書かない
- 確認できなかった軸は `未確認` と書く。`なし` と `未確認` を混同しない
- PDFの中身を見ずに「会派別賛否あり」と書かない。必ず開いて表の構造を見る
- 1ページだけ見て「全議案がこの形式」と断定しない。最低2会期分を見る

---

## 調査手順

### Step 1: 入口を押さえる

以下を特定して記録する。以降の調査はここを起点にする。

| 入口 | 探し方 |
|---|---|
| 議会公式サイト | 「<自治体名> 市議会」。市サイト配下か独立ドメインか |
| 会議録検索システム | 議会サイトの「会議録」リンク。別ドメインのASPに飛ぶことが多い |
| 議会だより | 「<自治体名> 議会だより」。**会派別賛否はここに載っていることが多い** |
| 公式YouTubeチャンネル | 「<自治体名> 公式 YouTube」。記者会見・本会議中継 |
| オープンデータポータル | 「<自治体名> オープンデータ」。CSV/APIがあれば最優先 |
| robots.txt | `https://<ドメイン>/robots.txt` |

> **会議録検索システムのベンダー判定が最も効く。**
> 複数の議会が同じASPを使っている場合、URL構造と検索パラメータが共通なので、
> 一般質問の取り込みコストがほぼゼロになる。
> HTMLのフッター・meta・JSのパスからベンダー名を控え、既知のものと一致するか確認する。
> （既知のベンダーと対応議会のリストは、調査を重ねながら本ファイル末尾に追記していく）

### Step 1.5: robots.txt を確認する

```bash
curl -s "https://<自治体のドメイン>/robots.txt"
```

クロール拒否の指定があれば、その範囲を記録する。
議会関係のパスが `Disallow` に含まれている場合は、調査でもそのパスを取得しない。

### Step 2: 14軸を調査する

後述の「判定軸」の表に沿って1軸ずつ埋める。

### Step 3: PDFは機械で判定する

目視だけで「テキストが取れるか」を判断しない。必ず実際に抽出する。

**議案本文だけでなく、議決結果PDFも必ず抽出にかけること。**
議決結果が画像PDFの自治体が実在する（2ページで抽出文字数2文字という例を確認）。
この場合、議案一覧すら OCR なしでは作れず、**Tier 1 の成立判定が変わる。**

```bash
# 作業ディレクトリはスクラッチパッドを使う（リポジトリを汚さない）
curl -sL "<PDFのURL>" -o /tmp/survey.pdf

# ページ数・用紙の向き（Page size の幅>高さ なら横型）
pdfinfo /tmp/survey.pdf

# テキスト層の有無。文字数が極端に少なければ画像PDF＝OCRが必要
pdftotext /tmp/survey.pdf - | wc -m

# 表の崩れ方を見る（-layout で列が保てるかが取り込みコストを左右する）
pdftotext -layout /tmp/survey.pdf - | head -60
```

判定の目安:

| 結果 | 判定 | 取り込みコスト |
|---|---|---|
| 1ページあたり数百文字以上 | テキスト層あり | 低 |
| 全体で数十文字以下 | 画像PDF（要OCR） | 高 |
| `-layout` で列が揃う | 表として機械処理可能 | 低 |
| `-layout` でも列が崩れる | 1件ずつ目視照合が必要 | 中〜高 |

#### 議案一覧PDFによくある落とし穴

規模の異なる3自治体で試したところ、全件に出た。レポートの「実装上の注意点」に必ず書くこと。

- **件名が長いと2〜3行に折り返され、議案番号の行と分離する。**
  行単位でパースすると件名が欠ける。番号の行を起点に、次の番号までを1レコードとして束ねる
- **議案番号の接頭辞が複数種類ある**（議案第／報告第／認定第／諮問第／同意第 など）。
  「報告」は議決されず結果欄が `─` や「質疑のみ」になる。status マッピング表を先に作る
- **議決結果の表記ゆれ**（可決／認定／可決及び認定／原案可決／原案適任／報告受理）
- **日付が全角数字のことがある**（`９月１日`）。正規化が必要
- **縦書きの表ヘッダは1文字ずつ分解される。** 会派名を抽出テキストから復元するのは非現実的なので、
  列の並び順を定数でマッピングし、年度が変わったら目視で照合する

### Step 3.5: Tier 2 は「厚み」を実測する（最重要）

**議案の説明が「存在するか」ではなく「解説を作れる厚みがあるか」で判定する。**
資料の有無だけで Tier 2 を○にすると、ほぼ必ず判定を誤る。

#### 手順

**条例改正の議案を3件**選び、その議案について書かれている説明文を実際に数える。
予算議案は厚く書かれる傾向があるので、**サンプルに予算議案を選ばない**こと
（厚く見えて実態を見誤る）。

```bash
# 会議録PDFから、ある議案の説明部分を抜き出して文字数を見る
pdftotext kaigiroku.pdf - | grep -A 10 "議案第１３号" | wc -m
```

数えるのは**実質的な情報量**であって、文字数そのものではない。
提案理由説明には全議案共通の定型句が入るので、それを除いて評価する。

> 実測例（ある町議会の会議録）。条例改正の提案理由はこの形だった。
>
> 「議案第○号 ○○条例の一部を改正する条例についてでありますが、**高校生を無償化する
> ための見直しを行うに当たり**、本条例の一部を改正する必要があるため、地方自治法第96条
> 第1項第1号の規定により、議会の議決を求めるものであります。」
>
> 約100字のうち、実質的な情報は太字の20字程度。**何がどう変わるか、対象は誰か、
> 財源はどうかは書かれていない。** 同じ会議録でも予算議案は総額・対前年度比・
> 編成方針まで厚く説明されており、**議案種別で厚みがまったく違う。**

#### 判定

文字数で機械的に切らない。**「何がどう変わるか」が読み取れるかで判断する。**

| 判定 | 条件 |
|---|---|
| **◯** | 条文そのもの、または改正内容が具体的に書かれている（何を・どう変えるか、対象、効果のいずれかが分かる） |
| **△** | 改正の方向性は分かるが、変更内容・対象・影響までは書かれていない |
| **✗** | 件名の言い換えに留まり、件名以上の情報がない |

**△ と ✗ は Tier 2 不成立として扱い、補強手段とその工数をレポートに書く。**
「提案理由説明がある」とだけ書いて○にしない。

判定した根拠として、**サンプルした議案の説明文を1件そのままレポートに引用する。**
読んだ人が同じ判断をできるようにするため。

#### 会議録の提案理由説明は「その主な内容は」節の有無で見分ける

実地で比較したところ、提案理由説明の書式に2つの型があり、**厚みの差がここに出る。**

**◯ の型**（改正内容が書かれている）

> 本案は、<法令>が公布されたことに伴い、関係条例である<条例名>の一部を改正しようとするものであります。
> **その主な内容は、<具体的な改正内容>しようとするものであります。**

根拠・背景の文に続いて「その**主な内容**は」または「その**内容**は」の節があり、
そこに何をどう変えるかが書かれている。この型なら Tier 2 は成立する。

**✗ の型**（件名の言い換えで終わる）

> 本案は、<件名の言い換え>を行うに当たり、本条例の一部を改正する必要があるため、
> 地方自治法第96条第1項第1号の規定により、議会の議決を求めるものであります。

地方自治法の条文引用で締めており、内容を説明する節がない。
件名以上の情報が得られないため Tier 2 は成立しない。

```bash
# 「その主な内容は」「その内容は」が議案数に見合う回数出てくるか数える
pdftotext kaigiroku.pdf - | grep -cE "その主な内容は|その内容は"
```

議案件数に対してこの節がほとんど出てこないなら ✗ 型を疑う。
ただし**節があっても中身が薄い場合はある**ので、最後は読んで判断すること。

### Step 3.6: 議案本文の探索先は議会サイトだけではない

議会サイトのメニューに議案本文がなくても、`なし` と判定しない。
**以下を全部あたってから判定する。**

| 探索先 | 探し方 | 取れるもの |
|---|---|---|
| 議会サイトの定例会ページ | 「○年○月定例会議案」等のPDF | 議案本文（複数議案が1ファイルのことが多い） |
| **所管課のページ** | 市サイト側で「条例改正」「パブリックコメント」 | 改正の概要資料。議会サイトより分かりやすいことがある |
| **例規集** | `d1-law.com` 等の共通ASP。「<自治体名> 例規集」 | 現行条文。**改正前後の差分を取る材料になる** |
| 予算書・予算説明資料 | 財政課のページ | 予算議案の内訳 |
| 議会だより | 議会サイト | 主要議案の解説（網羅性はないが平易） |
| 会議録の提案理由説明 | 会議録PDF/ASP | Step 3.5 で厚みを実測する |

**例規集は見落としやすいが有力。** 条例の一部改正なら、現行条文が取れれば
「改正後がどうなるか」を示せる。共通ASPを使っている自治体が多く、URL構造も共通。

#### ソースが複数あるときは全部記録する

AI解説のソースになりうる資料が複数見つかることがある
（議案本文はあるが画像PDF、同時に会議録の提案理由説明もある、など）。

**どれか1つに決めず、見つかったソースと取得コストを全部レポートに書く。**
取得コストの安さだけでルートを決められないことがあるため、
選択は実装時に運営者が判断できるようにしておく。

| ソース | 取得コストの目安 |
|---|---|
| 議案本文（HTML・テキストPDF） | 低 |
| 議案本文（画像PDF） | 高（OCRが必要） |
| 会議録の提案理由説明 | 低〜中（ASP経由ならAPI実装が必要） |
| 例規集の現行条文 | 低（共通ASPならURL構造が共通） |

### Step 3.7: 網羅性を確認する

「議決結果には全件あるが、本文が取れるのは一部だけ」というケースがある。

```
議決結果PDFの議案件数  と  本文が取れる議案件数  を数えて突き合わせる
```

一致しない場合は、**どの種別が欠けるか**（予算のみ本文あり、議員提出議案は本文なし 等）を
レポートに書く。欠けている種別が多いなら Tier 2 は部分的にしか成立しない。

### Step 4: URL安定性を確認する

**1回の調査では判定できない軸。** 以下のいずれかで確認する。

- Wayback Machine で同じ資料の過去URLを引き、現在のURLと一致するか
- 資料一覧ページのリンク先IDに規則性があるか（連番か、ハッシュか）
- 一定期間後に再調査する前提で `要再確認` と記録する

> 実運用中の地域版で、委員会議事録が**公開のたびに DocumentID を再採番され直リンクが壊れた**実績がある。
> このためURL直リンクを捨て、(開催日 × 委員会名) で突合する設計に変更した。
> 同じ罠がある自治体は少なくないはずなので、必ずこの軸を残す。

### Step 5: Tier を判定してレポートを書く

`docs/surveys/<YYYYMMDD>_<自治体名>調査.md` に出力する。
テンプレートは後述。

## 判定軸

### A. 議案まわり

| # | 軸 | 探す場所 | 取りうる値 |
|---|---|---|---|
| 1 | 議案一覧 | 議会サイト「議案」「議決結果」 | `HTML表` / `PDF一括` / `件名のみ` / `なし` |
| 2 | 議案本文 | 議案一覧からのリンク | `HTML` / `テキストPDF` / `画像PDF` / `提案理由のみ` / `なし` |
| 3 | PDFの体裁 | Step 3 の `pdfinfo` | `横型` / `縦型` / `複数議案が1ファイル` |
| 4 | 議決結果の粒度 | 議決結果ページ、議会だより | `非公開` / `可否のみ` / `票数のみ` / `会派別` / `議員別` |
| 5 | 議決結果の所在 | 同上 | `議案ページ` / `議案一覧PDFに同梱` / `議会だよりPDF` / `Excel` / `なし` |

軸4は**この調査で最も間違えやすい**。「議決結果」ページがあっても中身が可否のみのことが多い。
会派別・議員別の○×表は議会だよりPDFの後ろのほうに載っていることが多いので、必ずそちらも見る。

実例（2026-10-03 の調査）:

| 規模 | 議決結果ページの粒度 | 実際に取れる最大粒度 | 所在 |
|---|---|---|---|
| 政令指定都市 | 会派別 | **会派別**（9会派の○×） | 議案一覧PDFに同梱 |
| 中規模市 | 全員一致/賛成多数 | **議員別**（議員名＋会派名） | **議会だよりPDF** |
| 町（議員定数11） | 賛成数/反対数 | **票数のみ** | 議案一覧PDFに同梱 |

中規模市の例は、議決結果ページだけ見ると「会派別賛否なし」と誤判定する典型。
小規模な町村議会は会派が機能しておらず、`会派別` という軸自体が成立しないこともある。
**賛否の表現が自治体ごとに4段階ある前提で判定すること。**

### B. 会議録まわり

| # | 軸 | 探す場所 | 取りうる値 |
|---|---|---|---|
| 6 | 本会議会議録 | 会議録検索システム | `全文検索システム` / `PDF` / `要旨のみ` / `なし` |
| 7 | 速報版 | 同上 | `あり` / `なし`。公開までのラグ（何日/何ヶ月）も記録 |
| 8 | 委員会記録 | 議会サイト「委員会」 | `全文` / `要約` / `なし`。発言者が `記名` / `匿名` かも記録 |
| 9 | 会期日程 | 議会サイト「日程」「招集告示」 | `構造化` / `告示PDF` / `なし` |

軸7のラグは鮮度に直結する。「定例会終了後3ヶ月で確定版のみ」なら、
会期中のコンテンツは議案情報だけで作る前提になる。

軸8の「匿名・要約」は実在する。質問者名が出ない要約Q&A形式だと、
議員別の活動を見せる作りにはできない。

### C. その他のコンテンツ

| # | 軸 | 探す場所 | 取りうる値 |
|---|---|---|---|
| 10 | 市長記者会見 | 公式サイト「記者会見」、YouTube | `動画＋文字起こし` / `動画のみ` / `要旨テキスト` / `なし` |
| 11 | 議員・会派名簿 | 議会サイト「議員紹介」 | `HTML` / `PDF` / `なし`。会派の構成が分かるか |
| 12 | 予算・事務事業評価 | 市サイト「財政」「行政評価」 | `PDF公開` / `なし`。年度の遡及範囲も記録 |
| 13 | robots.txt | Step 1.5 を参照 | `制限なし` / `Disallow あり`（対象パスも記録） |
| 14 | URL安定性 | Step 4 | `固定` / `再採番あり` / `要再確認` |

軸10は自治体差が大きい。動画のみの場合、文字起こしを自前で作る必要がある
（既存の地域版ではYouTubeの文字起こしを基に構造化している）。

軸13はゲートなので Step 1.5 で先に確認しておくこと。ここでは結果を転記するだけでよい。

## 判定：Tier と2つの別軸

判定は**3つを別々に**出す。1つの数字にまとめない。

```
<自治体名>：Tier N ／ 賛否 = <粒度> ／ アーカイブ = <強さ>
```

### Tier（議案パイプラインの深さ）

みらい議会のコアは「議案をわかりやすく解説する」こと。
**Tier はこのパイプラインの深さだけで決める。** 賛否や一般質問は Tier に含めない。

| Tier | 作れるもの | 成立条件 |
|---|---|---|
| **Tier 0** | 財政の可視化、議員名簿 | **無条件**。財政は総務省「地方財政状況資料集」が全自治体共通フォーマットで公開されているため、議会サイトの出来に依存しない |
| **Tier 1** | 議案一覧（件名・議決結果・会期） | 軸1 が `なし` 以外 |
| **Tier 2** | **議案のAI解説** | 軸2 で**議案の内容を解説できる厚みの資料が取れる**こと。資料の有無ではなく、Step 3.5 で厚みを実測して判定する |

**Tier は累積。Tier 1 の条件を満たさなければ Tier 2 を名乗れない。**
Tier 2 に届かない自治体で「一般質問が取れるから上位」と判定してはいけない。

> **Tier 2 がこの調査で最も誤りやすい。** 「提案理由説明がある」「議案PDFがある」で
> ○にしてはいけない。実際に開いて厚みを測る（Step 3.5）、探索先を尽くす（Step 3.6）、
> 網羅性を見る（Step 3.7）の3つを通ってから判定すること。

### 障害の種類を区別する（最重要）

Tier 2 の判定では、**工数で解決できる障害と、公開されていないという解決できない障害を必ず分ける。**
ここを混ぜると、着手判断を根本的に誤る。

| 状態 | 記号 | 意味 | 打ち手 |
|---|---|---|---|
| テキストPDF / HTML | ◯ | そのまま取れる | — |
| **画像PDF・レイアウト崩れ** | **△** | **読めない形式だが原典は公開されている** | OCR・Vision・座標抽出。**金と時間で解決する** |
| **非公開・未掲載** | **✗** | **原典がそもそも公開されていない** | 情報公開請求、議会事務局への依頼、会議録での代替。**工数では解決しない** |

△ と ✗ は次元が違う。レポートでは必ず記号を使い分け、✗ の場合は代替手段を具体的に書く。

> 実例: ある政令指定都市の議案本文は89ページの画像PDFだった（△）。OCRをかければ条文が取れる。
> 別の中規模市では議案本文が見当たらなかった（✗ 相当）。OCRでは解決せず、会議録の提案理由説明で
> 代替できるかを確認するか、議会事務局に問い合わせる必要がある。
> **この2つを同じ Tier に置いてはいけない。**

### 別軸1：賛否の粒度

Tier とは独立。小規模町議会は会派が機能しておらず、`会派別` という軸自体が成立しない。

| 粒度 | 作れるもの |
|---|---|
| 議員別 | 議員ごとの賛否一覧。議会だよりPDFからの抽出になることが多い |
| 会派別 | 会派別賛否（既存のデータモデルがそのまま使える） |
| 票数のみ | 賛成数・反対数の表示 |
| 可否のみ | 可決/否決の表示のみ |
| 非公開 | — |

### 別軸2：アーカイブの強さ

一般質問・委員会記録・記者会見。Tier とは独立に評価する。

| 強さ | 条件 |
|---|---|
| 強 | 会議録が全文テキストで取れ、一般質問の回が特定できる |
| 中 | 会議録は全文テキストだが、回の内容が一覧から判別できない |
| 弱 | 要旨のみ、または画像PDF |
| なし | 公開されていない |

### まとめ方の例

```
政令指定都市A：Tier 2（△ 議案本文が画像PDF、OCR要）／ 賛否 = 会派別 ／ アーカイブ = 強
中規模市B　　：Tier 2（◯ 議案本文は未掲載だが、会議録の提案理由説明に改正内容あり）
               ／ 賛否 = 議員別（議会だよりPDF）／ アーカイブ = 強
町C　　　　　：Tier 1（✗ 議案本文なし。提案理由も件名の言い換えのみ）
               ／ 賛否 = 票数のみ ／ アーカイブ = 中
```

A と B は Tier が同じだが**成立の仕方が違う**。A は原典（議案本文）があり OCR の工数で解決する。
B は原典が未掲載だが会議録で代替できている。レポートには**どの資料で成立しているか**を書く。

B と C は「どちらも議案本文が取れない」が、**会議録の提案理由説明の厚みが違う**。
ここを実測せずに同じ扱いにすると判定を誤る。

> **B は実際に判定を2回誤った事例。** 最初は賛否と一般質問が取れることから Tier 3 とし（Tier 2 の
> 条件を確認していなかった）、次に議案本文が見つからないことから Tier 1 とした（会議録を
> 確認していなかった）。Step 3.5 と 3.6 を通して初めて Tier 2 に落ち着いた。
> **資料の有無で判断せず、探索先を尽くし、厚みを読むこと。**

## 既知の会議録検索システム

調査で判明したベンダーと対応議会をここに追記していく。
同じベンダーなら取り込みスクリプトを再利用できる。

| ベンダー / システム名 | 判別方法 | URL構造のメモ |
|---|---|---|
| `ssp.kaigiroku.net`（テナント型。フッターに `© DNP`） | 議会サイトの「会議録検索」が `ssp.kaigiroku.net` に飛ぶ | `http://ssp.kaigiroku.net/tenant/<自治体ローマ字>/pg/index.html`。配下に `MinuteSearch.html` / `SpTop.html` |
| （なし。自治体サイトに直接PDFを置く方式） | 外部ASPへのリンクが存在しない | 年別ページ → 定例会別ページ → PDF |

**調査の最初に `ssp.kaigiroku.net/tenant/<自治体ローマ字>/pg/index.html` を試す価値がある。**
テナント型なのでURL構造が共通で、ヒットすれば一般質問の取り込みコストが大きく下がる。

```bash
# ★ 必ずリダイレクトを追う（-L）。追わないと存在の有無にかかわらず 302 が返り判別できない
curl -sL -o /dev/null -w "%{http_code}\n" \
  "http://ssp.kaigiroku.net/tenant/<自治体ローマ字>/pg/index.html"
# 200 = テナントあり / 404 = テナントなし（またはテナント名が単純なローマ字ではない）
```

規模の異なる26自治体を単純ローマ字で試したところ**13件がヒット**した。
採用率は決して低くなく、**町・村でもヒットする**（人口数千規模の村でも採用例あり）。
ただしこれは単純ローマ字での試行結果なので、404 でも
**テナント名が別表記なだけの可能性がある。`なし` と断定せず、議会サイト側のリンクで裏を取ること。**

採用していない自治体は、自治体サイトにPDFを直接置いている。

### PDF直掲載方式のよくある階層

PDF直掲載の自治体は、規模が違っても同じ形のことが多い。CMS由来と思われる。

```
議決結果トップ（HTML）
  └ 年別ページ（HTML）     ← 年ラベルはここのリンクテキストから取る
      └ 定例会別ページ（HTML）
          └ PDF本体
```

> **CMSのスラッグは信用しない。** 年ラベルとURLスラッグが一致していない例を確認している
> （「令和7年」のページが `reiwa5_2`、「令和6年」が `reiwa5_1` というように、
> ページを複製して使い回した結果と思われるずれ方）。年はリンクテキストから取ること。
