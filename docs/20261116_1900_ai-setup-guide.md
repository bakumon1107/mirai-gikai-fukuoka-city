# AI エージェント向け セットアップ指示書

> **このファイルは AI コーディングエージェント（Claude Code・Codex CLI・Gemini CLI 等）に読ませるための指示書です。**
> 人間が読んで手作業で進めることもできます。
>
> 使い方（利用者向け）: 空のフォルダで AI エージェントを起動し、`○○市` を自分の地域に書き換えて貼り付けてください。
>
> ```
> ○○市のみらい議会を作りたいです。
> 次の指示書を要約せずに全文読んで、その手順に従って進めてください。
> https://raw.githubusercontent.com/bakumon1107/mirai-gikai-fukuoka-city/base-local/develop/docs/20261116_1900_ai-setup-guide.md
> ```
>
> 依頼はこの1回だけです。まず議会サイトを調べて何が作れるかを判定し、
> あなたが「着手する」と決めたら、GitHub と開発環境の用意に進みます。

---

## エージェントへ：この指示書の目的と守ること

**この指示書は要約せず、全文を読んでから始めてください。** Web 取得ツールが内容を要約してしまう場合は、
エージェント自身が `curl -fsSL <URL> -o <ファイル名>` で保存してから読みます
（利用者にコマンドを打たせない。保存先は clone 前の空フォルダでよい）。

利用者は、地方議会向けの「みらい議会」を自分の地域で立ち上げたい人です。
**Git・GitHub・ターミナルに慣れていない可能性が高い**前提で進めてください。

進め方は **「調査 → 作業者の着手承認 → GitHub と開発環境の用意」** の順です。
みらい議会の地域版は誰でも作れるため、作れるかどうか分からないまま fork したり、
同じ自治体の版を重複して作ったりしやすくなっています。
**作業者本人が調査結果と運営者としての責任を確認して「着手する」と決めるまで、fork・clone はしません。**

ゴールは次の状態です。

1. その自治体で何が作れるかの調査レポートが利用者の手元にある
2. 同じ自治体の既存の版の有無を確認し、作業者本人が着手を承認している（承認されなければここで終わり）
3. 利用者の GitHub アカウントに、テンプレートの fork（`mirai-gikai-<地域>`）があり、手元に clone されている
4. fork 直後の GitHub 設定と、自地域のブランチの準備が済んでいる
5. （希望があれば）ローカルでアプリが起動する

### 守ること

- **各ステップの前に、これから何をするかを専門用語を避けて1〜2文で説明する。**
  コマンドを実行したら、結果が何を意味するかも短く伝える
- **利用者の PC にソフトウェアをインストールする前は、必ず確認を取る。**
  インストール方法は OS ごとに提示し、管理者権限が要るものは利用者に実行してもらう
- **ログインやパスワード入力が必要な操作（`gh auth login` 等）は、利用者自身にターミナルで実行してもらう。**
  トークンやパスワードを聞き出したり、ファイルやコマンドに書き込んだりしない
- **元に戻せない操作（ブランチの削除、リポジトリの削除、強制 push）は、手順で指定された確認を取ってからでなければ行わない。**
  この指示書の中では行わない（ブランチの整理は council-survey Step 6 で一覧を見せて承認を得てから）
- **本家 `team-mirai/mirai-gikai` と配布元 `bakumon1107/mirai-gikai-fukuoka-city` には push も PR もしない。**
  操作対象は利用者自身の fork だけ
- エラーが出たら、同じコマンドを繰り返さず、エラー文を利用者に見せて原因を説明する。
  2回続けて同じ失敗をしたら、そこで止めて状況を報告する
- 例のコマンド中の `<アカウント>` `<地域>` は、利用者から聞いた値に置き換えて実行する。
  `<リポジトリ>` は利用者の fork のリポジトリ名で、通常は `mirai-gikai-<地域>`。
  Step 7B（既存の fork を使う場合）だけは既存の fork の名前になる
- **すでに済んでいる手順はやり直さない。** 利用者は、まったくの初心者から
  「ツールも fork もあり、設定だけ抜けている」人までさまざま。
  各ステップは「確認 → 足りないものだけ実施」の順で進め、済んでいれば「済んでいるので飛ばします」と伝えて次へ進む

## Step 0: いまの状態を調べ、対象を確認する

### 0-1. いまの状態を調べる

質問する前に、読み取りのコマンドで環境を確認します。**ここで分かったことは質問しない。**

```bash
pwd
git rev-parse --show-toplevel 2>/dev/null && git remote -v && git branch --show-current
git --version; node --version; pnpm --version; gh --version; docker --version; pdfinfo -v
gh auth status
```

| いまの状態 | 進め方 |
|---|---|
| 空のフォルダ、または何も無い | 0-2 から順に |
| すでに fork を clone したフォルダにいる（`origin` が利用者の `mirai-gikai-*`） | 0-2 → 調査（Step 1〜3）はこのまま行う。承認後は Step 8 の確認から |
| 地域版のブランチ（`<地域>/develop`）まで作ってある | すでに着手済み。調査が済んでいるかを利用者に確認し、済んでいれば Step 8 の確認から |

別の作業中のリポジトリ（無関係のプロジェクト）の中で起動されていた場合は、
そこでは作業せず、新しいフォルダを作るか利用者に場所を確認します。

### 0-2. 対象の自治体を確かめ、調査を始めることを伝える

地域名は依頼文の「○○市のみらい議会を作りたい」から読み取ります（書かれていなければ聞く）。
同名の自治体がある場合や、市と県の区別が無い場合は、ここで確定させます。

そのうえで、**次の1回の確認だけ**して調査に進みます（council-survey の Step 0 にあたる）。

> 「○○市議会の公式サイトと会議録を読み取りで調べ、みらい議会のどの機能まで作れるかを判定します。
> サイトへの書き込みや登録はしません。数十ページ程度を順に読みます。
> 判定結果を見てから、作り始めるかどうかを決めていただきます。進めてよいですか？」

了承が得られなければ、ここで終えます。

GitHub のアカウント名や PC の種類は、**この時点では聞きません**（着手が決まってから Step 5 で聞く）。

## Step 1: 調査に必要なツールを確認する

調査で必要なのは、議会の PDF を読むための poppler（`pdfinfo` / `pdftotext`）と `curl` だけです。
Git・Node.js・GitHub CLI などは、着手が決まってから用意します。

足りなければ、**入れてよいか確認してから**案内します。PC の種類が分からなければ、ここで聞きます。

| ツール | Mac | Windows（WSL2） | Windows（そのまま） | Linux |
|---|---|---|---|---|
| poppler | `brew install poppler` | `sudo apt install poppler-utils` | `scoop install poppler` 等 | `sudo apt install poppler-utils` 等 |
| curl | 標準で入っている | 標準で入っている | Git for Windows に付属（Git Bash） | 標準で入っていることが多い |

Windows の進め方（WSL2 か、そのままか）は Step 5 で詳しく扱います。
調査だけなら、Windows のままでも poppler を入れれば進められます。

## Step 3: 重複を確認し、作業者本人の着手承認を得る

調査手順書の **Step 5.5** をそのまま実行します。要点は次のとおりです。

1. 同じ自治体の既存の版を GitHub と Web で探し、見つかれば一覧にして、既存の運営者への連絡・合流を先に検討するよう提案する
2. 判定結果・運営者の名義・立場の開示・FORK_GUIDELINES の義務・ソースコードの公開・中立性を示し、

調査レポートが手元に残っていること、気が変わったら同じ文面でもう一度依頼すればよいことを伝えます。

承認が得られたら、以降の Step 4〜9 で GitHub と開発環境を用意します。

## Step 7: fork して手元に置く

### 7-1. すでに mirai-gikai 系の fork を持っていないか確認する

GitHub では、**1つのアカウントが同じ系統のリポジトリを fork できるのは1回だけ**です。

```bash
for r in $(gh repo list <アカウント> --fork --limit 200 --json name --jq '.[].name'); do
  echo "$r <- $(gh api repos/<アカウント>/$r --jq '.source.full_name')"
done | grep 'team-mirai/mirai-gikai$'
```

`gh repo list` の `parent` フィールドは null で返ることがあるため、判定には使わず、
REST API の `source`（fork ネットワークの大元）で判定します。

何も表示されなければ、fork はまだありません。`<リポジトリ>` を `mirai-gikai-<地域>` として 7-2 に進みます。

何か表示されたら、**それがこのテンプレートから作った fork か、別の用途の fork か**を確かめます。

```bash
gh api repos/<アカウント>/<表示されたリポジトリ名> --jq '.parent.full_name'
```

| 結果 | 意味 | 進め方 |
|---|---|---|
| `bakumon1107/mirai-gikai-fukuoka-city` | 以前このテンプレートから作った fork（やり直し・続き） | `<リポジトリ>` をその名前にして、7-2 の 2.（clone）から。手元に clone 済みならそこへ移動して Step 8 へ |
| それ以外 | 本家や別の地域版から作った、**別の用途の fork** | `<リポジトリ>` をその名前にして **7B** へ |

7B に進む場合は、先に利用者へ次のことを伝えて了承を得てください。

- 1つのアカウントに同じ系統の fork は1つしか作れないため、**既存の fork の中にテンプレートのブランチを足して使う**こと
- 既存の fork ですでにサービスを運用している場合、その運用中のブランチや既定ブランチには触らないこと
- 新しい地域用に、別の GitHub アカウント（または Organization）を作って fork する方法もあり、そのほうが混ざらないこと

### 7-2. fork して clone する

```bash
# 1. fork する（全ブランチがコピーされる。--default-branch-only は付けない）
gh repo fork bakumon1107/mirai-gikai-fukuoka-city --fork-name mirai-gikai-<地域> --clone=false

# 2. 作業用フォルダに clone して、テンプレートのブランチに移る
git clone https://github.com/<アカウント>/<リポジトリ>.git
cd <リポジトリ>
git switch base-local/develop
```

fork の作成は GitHub 側で数秒〜数十秒かかることがあります。
直後の `git clone` が「Repository not found」で失敗したら、少し待ってから1回だけやり直してください。

clone 直後は配布元の既定ブランチ（`fukuoka-city/develop`）になっていますが、
`git switch base-local/develop` で切り替われば正常です。

利用者には、「fork ＝ 元のプロジェクトとのつながりを保ったまま、自分用のコピーを GitHub 上に作ること」と説明してください。
`git clone` だけで別リポジトリを作るとこのつながりが切れ、後から戻せません。

clone 前の作業フォルダに保存した調査レポートや指示書は、clone したリポジトリの中に移さないでください
（調査レポートはコミットしない決まり）。

### 7B. すでに別の用途の fork を持っている場合

既存の fork を clone し、テンプレートを remote として追加します。

```bash
git clone https://github.com/<アカウント>/<リポジトリ>.git
cd <リポジトリ>
git remote add template https://github.com/bakumon1107/mirai-gikai-fukuoka-city.git
git fetch template base-local/develop
git switch -c base-local/develop template/base-local/develop
git push -u origin base-local/develop
```

既存の fork にすでに `base-local/develop` がある場合は、push が拒否されることがあります。
その場合は上書きせず、利用者に状況を伝えて止まってください（強制 push はしない）。

既存の fork にある別の用途のブランチや既定ブランチには、ここでも以降でも触りません。

## Step 8: fork 直後の GitHub 設定

fork は元の設定を引き継がず、一部の機能が止まった状態で作られます。まず現状を確認し、済んでいない項目だけ実行します。

```bash
gh repo set-default --view                                # 利用者の fork が出れば済んでいる
gh repo view <アカウント>/<リポジトリ> --json hasIssuesEnabled
git remote -v | grep template                             # 出れば template は登録済み
```

```bash
# gh の操作先を自分の fork にする（これを忘れると PR が本家に向く）
gh repo set-default <アカウント>/<リポジトリ>
gh repo set-default --view

# Issues を有効にする
gh repo edit <アカウント>/<リポジトリ> --enable-issues

# テンプレート配布元を remote として登録する（7B の場合は済んでいる）
git remote add template https://github.com/bakumon1107/mirai-gikai-fukuoka-city.git
git fetch template base-local/develop
```

**GitHub Actions の有効化は利用者にブラウザで操作してもらいます。**
次の URL を開き、`I understand my workflows, go ahead and enable them` を押すよう案内してください。

```
https://github.com/<アカウント>/<リポジトリ>/actions
```

ボタンが無く、ワークフロー一覧が表示されていれば有効になっています。

続けて、clone したフォルダの `AGENTS.md`（`CLAUDE.md`・`GEMINI.md` は同じ内容へのリンク）を読みます。
以降の作業はこのリポジトリのルールにも従います。

その後、**調査手順書の Step 6（自地域のブランチ作成・既定ブランチの変更・不要ブランチの整理・参照の置き換え）**を実行します。
7B（既存の fork を使う）で進めた場合は、ブランチの削除と既定ブランチの変更は行いません（手順書の 4-0 で判定される）。

## Step 9: ローカルでアプリを起動する（希望する場合）

「手元で画面を見てみたいか」を利用者に聞き、希望すれば進めます。「後でよい」と言われたら Step 10 へ進みます。

Docker が起動していることを確認してから実行します。

```bash
pnpm install --frozen-lockfile
cp .env.example .env
npx supabase start      # 初回は数分かかる
pnpm db:reset           # DB の初期化とサンプルデータ投入
pnpm dev
```

起動したら、次を利用者にブラウザで開いてもらいます。

| 画面 | URL | 備考 |
|---|---|---|
| 公開サイト | http://localhost:3002 | 架空の「サンプル市」のデータが表示される |
| 管理画面 | http://localhost:3001 | `admin@example.com` / `admin123456` |

`pnpm dev` は止めるまで動き続けるコマンドです。**エージェントの実行を止めてしまわないよう、
バックグラウンドで実行するか、利用者に別のターミナルで実行してもらってください。**
止めるときは Ctrl+C、DB も止めるときは `npx supabase stop` を案内します。

うまくいかない場合の典型例:

| 症状 | 確認すること |
|---|---|
| `supabase start` が失敗する | Docker Desktop が起動しているか。エラー文に設定ファイル（`config.toml`）の項目名が出ていれば、Supabase CLI の版の違いが原因の可能性がある |
| `pnpm install` で Node のバージョンエラー | `node --version` が 24 系か |
| ポートが使用中 | `.env` の `WEB_PORT` / `ADMIN_PORT` を変える |
