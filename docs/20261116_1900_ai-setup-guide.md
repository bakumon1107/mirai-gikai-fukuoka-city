# AI エージェント向け セットアップ指示書

> **このファイルは AI コーディングエージェント（Claude Code・Codex CLI・Gemini CLI 等）に読ませるための指示書です。**
> 人間が読んで手作業で進めることもできます。
>
> 使い方（利用者向け）: 空のフォルダで AI エージェントを起動し、`○○市` を自分の地域に書き換えて貼り付けてください。
>
> ```
> ○○市のみらい議会を作りたいです。
> 次の指示書を要約せずに全文読んで、その手順に従って開発環境の用意から始めてください。
> https://raw.githubusercontent.com/bakumon1107/mirai-gikai-fukuoka-city/base-local/develop/docs/20261116_1900_ai-setup-guide.md
> ```
>
> 依頼はこの1回だけで、環境の用意が終わるとそのまま議会サイトの調査に進みます。

---

## エージェントへ：この指示書の目的と守ること

**この指示書は要約せず、全文を読んでから始めてください。** Web 取得ツールが内容を要約してしまう場合は、
エージェント自身が `curl -fsSL <URL> -o ai-setup-guide.md` で保存してから読みます
（利用者にコマンドを打たせない。保存先は clone 前の空フォルダでよい）。

利用者は、地方議会向けの「みらい議会」を自分の地域で立ち上げたい人です。
**Git・GitHub・ターミナルに慣れていない可能性が高い**前提で進めてください。

ゴールは次の状態です。

1. 利用者の GitHub アカウントに、テンプレートの fork（`mirai-gikai-<地域>`）がある
2. その fork が手元に clone され、`base-local/develop` ブランチになっている
3. fork 直後の GitHub 設定が済んでいる
4. （希望があれば）ローカルでアプリが起動する
5. 続けて、その地域の議会サイトの調査（`council-survey`）が始まっている

### 守ること

- **各ステップの前に、これから何をするかを専門用語を避けて1〜2文で説明する。**
  コマンドを実行したら、結果が何を意味するかも短く伝える
- **利用者の PC にソフトウェアをインストールする前は、必ず確認を取る。**
  インストール方法は OS ごとに提示し、管理者権限が要るものは利用者に実行してもらう
- **ログインやパスワード入力が必要な操作（`gh auth login` 等）は、利用者自身にターミナルで実行してもらう。**
  トークンやパスワードを聞き出したり、ファイルやコマンドに書き込んだりしない
- **元に戻せない操作（ブランチの削除、リポジトリの削除、強制 push）はこの指示書の範囲ではやらない。**
  ブランチの整理は、調査で着手が決まった後の別の手順（fork手順 セクション4）で行う
- **本家 `team-mirai/mirai-gikai` と配布元 `bakumon1107/mirai-gikai-fukuoka-city` には push も PR もしない。**
  操作対象は利用者自身の fork だけ
- エラーが出たら、同じコマンドを繰り返さず、エラー文を利用者に見せて原因を説明する。
  2回続けて同じ失敗をしたら、そこで止めて状況を報告する
- 例のコマンド中の `<アカウント>` `<地域>` は、Step 0 で聞いた値に置き換えて実行する。
  `<リポジトリ>` は利用者の fork のリポジトリ名で、通常は `mirai-gikai-<地域>`。
  Step 4B（既存の fork を使う場合）だけは既存の fork の名前になる
- **すでに済んでいる手順はやり直さない。** 利用者は、まったくの初心者から
  「ツールも fork もあり、設定だけ抜けている」人までさまざま。
  各ステップは「確認 → 足りないものだけ実施」の順で進め、済んでいれば「済んでいるので飛ばします」と伝えて次へ進む

## Step 0-A: いまの状態を調べる（最初に必ず行う）

質問する前に、利用者の環境がどこまで用意できているかを読み取りのコマンドで確認します。
**ここで分かったことは、Step 0 で質問しない。**

```bash
pwd
git rev-parse --show-toplevel 2>/dev/null && git remote -v && git branch --show-current
git --version; node --version; pnpm --version; gh --version; docker --version
gh auth status
```

結果に応じて、始める場所を決めます。

| いまの状態 | 進め方 |
|---|---|
| 何も無い（ツール不足・未ログイン） | Step 0 から順に |
| ツールとログインは済んでいる | Step 0 の質問のあと、Step 2 後半（Git の名前・メール）を確認して Step 3 へ |
| すでに fork を clone したフォルダにいる（`origin` が利用者の `mirai-gikai-*`） | Step 5 の確認から。`base-local/develop` が無ければ Step 4B の `template` remote 手順で取り込む |
| 地域版のブランチ（`<地域>/develop`）まで作ってある | Step 5 の確認のあと Step 7 へ |

別の作業中のリポジトリ（無関係のプロジェクト）の中で起動されていた場合は、
そこでは作業せず、新しいフォルダを作るか利用者に場所を確認します。

## Step 0: 最初に聞くこと

作業を始める前に、次の項目をまとめて質問してください。
**依頼文にすでに書かれている項目は聞き直さない**こと
（特に地域名は、依頼文の「○○市のみらい議会を作りたい」から読み取る）。

| 質問 | 使い道 |
|---|---|
| GitHub のアカウント名（持っていなければ「まだ無い」） | fork 先 |
| 作りたい地域（例: 渋谷区、小諸市） | 調査対象・リポジトリ名・ブランチ名 |
| その地域のローマ字表記（小文字・ハイフン可。例: `shibuya`、`komoro`） | `mirai-gikai-<地域>` |
| 使っている PC（Mac / Windows / Linux） | インストール方法 |

GitHub アカウントが無い場合は、https://github.com/signup で作成してもらい、作成後に続けます。

ローマ字表記は、聞く前に自治体の公式サイトのドメイン
（例: `city.komoro.lg.jp` → `komoro`）から候補を作り、「`komoro` でよいですか？」の形で確認してください。

依頼文が地域名を含まない形（例: 「次の指示書に従って開発環境を用意してください」だけ）でも、
ここで地域名を聞けば以降は同じ流れで進められます。

## Step 1: 必要なツールがそろっているか確認する

次のコマンドで確認します。

```bash
git --version
node --version     # v24.x であること
pnpm --version
gh --version
docker --version   # ローカルでアプリを起動する場合のみ必要
pdfinfo -v         # 調査（Step 7）で議会の PDF を読むのに必要
```

足りないものがあれば、**一覧にして利用者に見せ、インストールしてよいか確認してから**案内します。

| ツール | 用途 | Mac | Windows | Linux |
|---|---|---|---|---|
| Git | ソースコードの管理 | `xcode-select --install` または `brew install git` | 下の「Windows の場合」を参照 | `sudo apt install git` 等 |
| Node.js 24 | アプリの実行 | `brew install node@24` または nvm / fnm | 同上 | nvm / fnm |
| pnpm | パッケージ管理 | `npm install -g pnpm` | 同上 | `npm install -g pnpm` |
| GitHub CLI (`gh`) | GitHub の操作 | `brew install gh` | 同上 | https://github.com/cli/cli/blob/trunk/docs/install_linux.md |
| Docker | ローカル DB | Docker Desktop | Docker Desktop | Docker Engine |
| poppler（`pdfinfo` / `pdftotext`） | 調査で議会の PDF を読む | `brew install poppler` | 同上 | `sudo apt install poppler-utils` 等 |

**Windows の場合**は、次のどちらかで進めます。アプリ自体は Windows でもそのまま動きます。

| 進め方 | 向いている人 | 準備 |
|---|---|---|
| **WSL2（Ubuntu）の中で作業する（推奨）** | 特にこだわりが無い人。手順書のコマンドがそのまま動き、つまずきが少ない | 管理者権限の PowerShell で `wsl --install` → 再起動。以降は WSL2 のターミナルで、表の「Linux」列の方法で入れる |
| Windows のまま作業する | WSL2 を入れたくない・入れられない人 | 下のコマンドで入れる |

Windows のまま作業する場合のインストール例（PowerShell で1行ずつ実行）:

```powershell
winget install Git.Git
winget install GitHub.cli
winget install Schniz.fnm
winget install Docker.DockerDesktop   # ローカルでアプリを起動する場合のみ
```

続けて Git Bash で:

```bash
fnm install 24 && fnm use 24
npm install -g pnpm
git config --global core.autocrlf input
```

poppler は `scoop install poppler` 等で入れ、`pdfinfo` に PATH が通っていることを確認します。

Windows のままで進める場合、この指示書と調査手順のコマンドは bash 用なので、
**Git Bash（Git for Windows に付属）で実行**します。PowerShell やコマンドプロンプトでは動きません。
エージェントのシェルが PowerShell の場合は、`bash -lc "..."` 経由で実行するか、利用者に WSL2 を勧めてください。

Docker はローカルでアプリを動かすときだけ必要です。調査（Step 7）だけなら後回しにできます。

## Step 2: GitHub にログインする

```bash
gh auth status
```

ログインしていなければ、**利用者自身に**次を実行してもらいます（ブラウザでの認証が入るため）。

```bash
gh auth login
```

選択肢は `GitHub.com` → `HTTPS` → `Login with a web browser` を案内します。
完了後、`gh auth status` で Step 0 のアカウント名でログインしていることを確認します。

続けて Git に名前とメールアドレスが設定されているか確認し、未設定なら利用者に値を聞いて設定します。

```bash
git config --global user.name
git config --global user.email
```

コミットに記録したメールアドレスは、公開リポジトリでは誰でも見られます。
個人のアドレスを出したくない利用者には、GitHub の非公開用アドレス
（`<ID>+<アカウント>@users.noreply.github.com`。GitHub の Settings → Emails で確認できる）を使う方法を案内します。

## Step 3: すでに mirai-gikai 系の fork を持っていないか確認する

GitHub では、**1つのアカウントが同じ系統のリポジトリを fork できるのは1回だけ**です。
すでに `mirai-gikai` 系の fork を持っていると、新しく fork できません。

```bash
for r in $(gh repo list <アカウント> --fork --limit 200 --json name --jq '.[].name'); do
  echo "$r <- $(gh api repos/<アカウント>/$r --jq '.source.full_name')"
done | grep 'team-mirai/mirai-gikai$'
```

何も表示されなければ、fork はまだありません。`<リポジトリ>` を `mirai-gikai-<地域>` として Step 4 に進みます。

何か表示されたら、すでに fork を持っています（表示されたのがそのリポジトリ名）。
**それがこのテンプレートから作った fork か、別の用途の fork か**を確かめます。

```bash
gh api repos/<アカウント>/<表示されたリポジトリ名> --jq '.parent.full_name'
```

| 結果 | 意味 | 進め方 |
|---|---|---|
| `bakumon1107/mirai-gikai-fukuoka-city` | 以前このテンプレートから作った fork（やり直し・続き） | `<リポジトリ>` をその名前にして、Step 4 の 2.（clone）から。手元に clone 済みならそこへ移動して Step 5 へ |
| それ以外 | 本家や別の地域版から作った、**別の用途の fork** | `<リポジトリ>` をその名前にして **Step 4B** へ |

Step 4B に進む場合は、先に利用者へ次のことを伝えて了承を得てください。

- 1つのアカウントに同じ系統の fork は1つしか作れないため、**既存の fork の中にテンプレートのブランチを足して使う**こと
- 既存の fork ですでにサービスを運用している場合、その運用中のブランチや既定ブランチには触らないこと
- 新しい地域用に、別の GitHub アカウント（または Organization）を作って fork する方法もあり、そのほうが混ざらないこと

`gh repo list` の `parent` フィールドは null で返ることがあるため、判定には使わないでください。
REST API の `source`（fork ネットワークの大元）で判定します。

## Step 4: fork して手元に置く

Step 3 で fork が見つからなかった場合だけ行います。
fork はあるが手元に clone が無い場合は、下の 2. だけ行います。

```bash
# 1. fork する（全ブランチがコピーされる。--default-branch-only は付けない）
gh repo fork bakumon1107/mirai-gikai-fukuoka-city --fork-name mirai-gikai-<地域> --clone=false

# 2. 作業用フォルダに clone して、テンプレートのブランチに移る
git clone https://github.com/<アカウント>/<リポジトリ>.git
cd <リポジトリ>
git switch base-local/develop
```

fork の作成は GitHub 側で数秒〜数十秒かかることがあります。
直後の `git clone` が「Repository not found」で失敗したら、少し待ってから1回だけやり直してください。

clone 直後は配布元の既定ブランチ（`fukuoka-city/develop`）になっていますが、
`git switch base-local/develop` で切り替われば正常です。

利用者には、「fork ＝ 元のプロジェクトとのつながりを保ったまま、自分用のコピーを GitHub 上に作ること」と説明してください。
`git clone` だけで別リポジトリを作るとこのつながりが切れ、後から戻せません。

Step 5 へ進みます。

### Step 4B: すでに fork を持っている場合

既存の fork を clone し、テンプレートを remote として追加します。

```bash
git clone https://github.com/<アカウント>/<リポジトリ>.git
cd <リポジトリ>
git remote add template https://github.com/bakumon1107/mirai-gikai-fukuoka-city.git
git fetch template base-local/develop
git switch -c base-local/develop template/base-local/develop
git push -u origin base-local/develop
```

既存の fork にすでに `base-local/develop` がある場合は、push が拒否されることがあります。
その場合は上書きせず、利用者に状況を伝えて止まってください（強制 push はしない）。

既存の fork にある別の用途のブランチや既定ブランチには、ここでも以降でも触りません。
Step 5 の `template` remote の追加は済んでいるので省略します。

## Step 5: fork 直後の GitHub 設定

fork は元の設定を引き継がず、一部の機能が止まった状態で作られます。

まず現状を確認し、済んでいない項目だけ実行します。

```bash
gh repo set-default --view                                # 利用者の fork が出れば済んでいる
gh repo view <アカウント>/<リポジトリ> --json hasIssuesEnabled
git remote -v | grep template                             # 出れば template は登録済み
```

```bash
# gh の操作先を自分の fork にする（これを忘れると PR が本家に向く）
gh repo set-default <アカウント>/<リポジトリ>
gh repo set-default --view

# Issues を有効にする
gh repo edit <アカウント>/<リポジトリ> --enable-issues

# テンプレート配布元を remote として登録する（Step 4B の場合は済んでいる）
git remote add template https://github.com/bakumon1107/mirai-gikai-fukuoka-city.git
git fetch template base-local/develop
```

**GitHub Actions の有効化は利用者にブラウザで操作してもらいます。**
次の URL を開き、`I understand my workflows, go ahead and enable them` を押すよう案内してください。

```
https://github.com/<アカウント>/<リポジトリ>/actions
```

ボタンが無く、ワークフロー一覧が表示されていれば有効になっています。

## Step 6: ローカルでアプリを起動する（希望する場合）

「手元で画面を見てみたいか」を利用者に聞き、希望すれば進めます。
**調査だけなら不要**なので、「後でよい」と言われたら Step 7 へ進みます。

Docker が起動していることを確認してから実行します。

```bash
pnpm install --frozen-lockfile
cp .env.example .env
npx supabase start      # 初回は数分かかる
pnpm db:reset           # DB の初期化とサンプルデータ投入
pnpm dev
```

起動したら、次を利用者にブラウザで開いてもらいます。

| 画面 | URL | 備考 |
|---|---|---|
| 公開サイト | http://localhost:3002 | 架空の「サンプル市」のデータが表示される |
| 管理画面 | http://localhost:3001 | `admin@example.com` / `admin123456` |

`pnpm dev` は止めるまで動き続けるコマンドです。**エージェントの実行を止めてしまわないよう、
バックグラウンドで実行するか、利用者に別のターミナルで実行してもらってください**（Step 7 に進めなくなるため）。
止めるときは Ctrl+C、DB も止めるときは `npx supabase stop` を案内します。

うまくいかない場合の典型例:

| 症状 | 確認すること |
|---|---|
| `supabase start` が失敗する | Docker Desktop が起動しているか。エラー文に設定ファイル（`config.toml`）の項目名が出ていれば、Supabase CLI の版の違いが原因の可能性がある |
| `pnpm install` で Node のバージョンエラー | `node --version` が 24 系か |
| ポートが使用中 | `.env` の `WEB_PORT` / `ADMIN_PORT` を変える |

## Step 7: そのまま議会サイトの調査に進む

ここまでで環境の用意は完了です。**利用者に依頼し直してもらわず、このセッションのまま調査に進みます。**

1. 利用者に、ここまでの要約を短く伝える（fork の URL、clone した場所、アプリを起動したかどうか）
2. clone したフォルダ（`<リポジトリ>`）の次のファイルを読む。
   以降はこの指示書ではなく、これらに従う
   - `AGENTS.md`（`CLAUDE.md`・`GEMINI.md` は同じ内容へのリンク）: このリポジトリでの作業ルール
   - `.claude/skills/council-survey/SKILL.md`: 議会サイトの調査手順
3. AGENTS.md の「新地域の立ち上げは調査から始める」に従い、
   **Step 0 で確認した地域を対象に、`council-survey` の手順を Step 1 から順に実行する。**
   スラッシュコマンドとして呼べない環境でも、SKILL.md を読んでその手順どおりに進める
   （「調査しますか？」と利用者に選ばせない）

調査の後は council-survey の手順どおり、何が作れるかの判定レポート → 着手するかの確認 →
着手が決まったら自地域のブランチ作成・不要ブランチの整理・各種設定の書き換え（council-survey Step 6）、と進みます。

**Step 4B（既存の fork を使う）で進めた場合は、council-survey Step 6 でも
不要ブランチの削除と既定ブランチの変更を行いません。** 既存の fork のブランチは利用者の別の用途のものです。
`<地域>/develop` の作成と参照の置き換えだけ行います。

### 利用者に添えて伝えること

- **次回以降は、clone したフォルダ（`<リポジトリ>`）で AI エージェントを起動すること。**
  そのフォルダで起動すれば、作業ルール（AGENTS.md）が自動で読み込まれます
- 公開前に必ず守るルールが、clone したフォルダの `FORK_GUIDELINES.md` にあること
  （サービス名・ロゴ・配色の変更、ソースコード公開先の明記など。AGPL-3.0 に基づく条件）
