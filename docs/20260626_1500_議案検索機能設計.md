# 議案検索機能 設計書

- 作成日: 2026-06-26
- 対象アプリ: `web/`（公開サイト / https://gikai.team-mir.ai/）
- ブランチ: `docs/bill-search-design`

## 1. 背景・課題

公開サイトはトップページで議案（bills）を **タグ別・注目・会期別** に並べて表示しているが、フリーワードでの**検索ボックスが存在しない**。会期（diet_sessions）が増え、過去会期も含めた掲載議案数が増加してきたため、「特定のキーワードを含む議案を探す」導線が必要になっている。

現状の議案発見手段:
- トップページのタグ別セクション（防災・医療福祉・産業 …）
- 注目の議案セクション
- 前回会期セクション（Archive）
- 会期別ページ `/kokkai/[slug]/bills`

→ いずれも「カテゴリで絞る」操作であり、横断的なフリーワード検索ができない。

## 2. 目的・スコープ

### 目的
掲載済み（`publish_status = 'published'`）の議案を、タイトル・要約等のフリーワードで横断検索できるようにする。

### スコープ
- **対象**: `web/`（公開サイト）の議案検索のみ。
- **In scope**: `/search` ページ、検索フォーム、検索ローダー/リポジトリ、ルート定義、入力サニタイズ。
- **Out of scope（将来課題）**: 全文（本文 `content`）検索の精度向上、AIセマンティック検索、検索結果のハイライト表示、サジェスト/オートコンプリート、検索ログ分析。

## 3. 現状調査

### 3.1 データモデル

| テーブル | 主な検索対象カラム | 備考 |
| --- | --- | --- |
| `bills` | `name`（正式名称）, `status`, `submitted_date`, `diet_session_id`, `publish_status` | 公開判定は `publish_status='published'` |
| `bill_contents` | `title`（わかりやすいタイトル）, `summary`（要約）, `content`（本文） | `bill_id` × `difficulty_level` で **複数行**。難易度ごとに別レコード |
| `bills_tags` / `tags` | `tags.label` | 多対多。絞り込み候補 |
| `diet_sessions` | `name`（例: 第219回臨時国会）, `slug` | 会期。結果表示に使用 |

- `bill_contents.difficulty_level` は enum（やさしい/詳しい等）。公開サイトは **Cookie 由来の難易度**を `getDifficultyLevel()` で取得して該当難易度のコンテンツを表示している（[get-difficulty-level](web/src/features/bill-difficulty/server/loaders/get-difficulty-level.ts)）。
- データアクセスは全て `createAdminClient()`（Secret Key）経由。RLSは有効だがポリシー無し（デフォルト全拒否）、認可はアプリ層で実装（AGENTS.md 準拠）。

### 3.2 既存の一覧表示

- 議案カードは [bill-card.tsx](web/src/features/bills/client/components/bill-list/bill-card.tsx) / [bill-list.tsx](web/src/features/bills/client/components/bill-list/bill-list.tsx)。`BillWithContent` 型（`Bill + bill_content + tags + ...`）を受け取って描画する。
- リポジトリ/ローダーの規約: データアクセスは [bill-repository.ts](web/src/features/bills/server/repositories/bill-repository.ts) に集約、ローダーで `unstable_cache` を併用（[get-bills.ts](web/src/features/bills/server/loaders/get-bills.ts)）。

### 3.3 先行事例（姉妹フォーク fukuoka-city/develop）

福岡市版フォークには **完成済みの `features/search/` 実装**が存在し、本設計の有力な雛形になる。

```
web/src/app/(main)/search/page.tsx
web/src/features/search/
├── client/components/search-form.tsx          # "use client" 検索フォーム（サジェストキーワード付き）
├── client/components/search-result-tabs.tsx
├── server/loaders/search-loader.ts            # Promise.all で各検索を集約
├── server/repositories/search-repository.ts   # PostgREST .or(ilike) で検索
└── shared/
    ├── types/search-types.ts
    └── utils/sanitize-search-query.ts (+ test) # 注入対策
```

福岡市版の特徴と、本設計（国会版）との差分:

| 観点 | 福岡市版 | 国会版（本設計） |
| --- | --- | --- |
| 検索対象 | bills / general_questions / budgets（タブ切替） | **bills のみ**（タブ不要） |
| 検索方式 | PostgREST `.or(title.ilike.%q%,summary.ilike.%q%)` | 同方式を採用（後述） |
| 難易度 | `'normal'` 固定 | **Cookie 由来の現在難易度**で絞る |
| 結果カード | 専用の軽量カード（独自型） | **既存 `BillCard` を再利用**（表示の一貫性） |
| 注入対策 | `sanitizeSearchQuery()` で構造文字 `, . ( ) *` を除去 | **同方式を踏襲（必須）** |

> 注: 福岡市版は別フォークのため直接 import はできない。`sanitizeSearchQuery` 等のロジックはコピーではなく本リポジトリの規約に沿って再実装する（純粋関数 + テスト必須）。

#### 既知のセキュリティ知見（必ず反映）

福岡市版のコミット `f70307a5`「検索のフィルタ注入対策」で、検索クエリを PostgREST の `or()` フィルタへ**エスケープなしで埋め込んでいた**ため、カンマ・ピリオド等を含む入力で意図しないフィルタ条件が注入され得る問題が修正されている（例: `a,id.neq.0` → `or=(title.ilike.%a,id.neq.0%, ...)` と解釈される）。本設計では**初期実装からサニタイズを組み込む**。

## 4. 設計方針：検索方式の選定

日本語は語境界（スペース）が無いため、PostgreSQL 標準の `to_tsvector`（英語前提のトークナイザ）は素の状態では使えない。候補を比較する。

| 方式 | 日本語対応 | Supabase Hosted | 実装コスト | 採否 |
| --- | --- | --- | --- | --- |
| **PostgREST `.or(ilike '%q%')`** | ◎（部分一致なので分かち書き不要） | ○ | 低（マイグレ不要） | **採用（Phase 1）** |
| pg_trgm GIN インデックス + ilike | ◎ | ○（拡張利用可） | 中（マイグレ要） | **採用（後続増分・性能対策）** |
| PGroonga / pg_bigm | ◎（最良） | **×（hosted 非対応）** | 高 | 不採用 |
| tsvector + 独自 bigram 分割 | △ | ○ | 高（保守重） | 不採用 |
| AI ベクトル検索（embeddings） | ◎（意味検索） | ○（pgvector） | 高 | 将来課題 |

### 判断

- **Phase 1 は PostgREST `.or(ilike)` を採用**する。理由:
  1. 部分一致のため日本語の分かち書きが不要で、現データ規模（数百〜低数千件）では `ilike '%q%'` のシーケンシャルスキャンでも体感上十分高速。
  2. マイグレーション不要で最短で価値提供できる。
  3. 姉妹フォークで実績がありパターンが確立している（保守者の認知負荷が低い）。
- **後続増分で pg_trgm GIN インデックスを追加**する。議案数が増えて `ilike` の seq scan が遅くなった時点での性能対策として、`bill_contents(title/summary)` と `bills(name)` に `gin_trgm_ops` インデックスを張る。`ilike '%q%'` はそのまま trigram インデックスで加速できるため、**アプリ側のコード変更は不要**（インデックス追加のみ）。
- 関連度ランキングや複合フィルタ（タグAND条件等）が必要になった段階で初めて、AGENTS.md の規約に沿った **RPC（DB function）+ 統合テスト** へ移行する。Phase 1 で RPC を作らないのは過剰設計を避けるため。

## 5. アーキテクチャ

Bulletproof React の feature ベース構成に従い、新規 feature `bill-search` を作成する。データは bills なので、リポジトリ/型/カードは既存 `bills` feature を再利用する。

```

web/src/features/bill-search/
├── server/
│   ├── loaders/search-bills.ts             # 難易度を取得しリポジトリを呼ぶ
│   └── components/search-results.tsx       # Server Component（結果リスト + 空状態）
├── client/
│   └── components/search-box.tsx           # "use client" 検索入力（form submit で /search?q= 遷移）
└── shared/

web/src/features/bills/server/repositories/bill-repository.ts

```

### 5.1 リポジトリ層（`bill-repository.ts` に追加）

```ts
/**
 * フリーワードで公開済み議案を検索（title / summary の部分一致）
 */
export async function findPublishedBillsBySearch(
  query: string,
  difficultyLevel: DifficultyLevelEnum
) {
  const safeQuery = sanitizeSearchQuery(query); // 構造文字除去（必須）
  const supabase = createAdminClient();
  const { data, error } = await supabase
    .from("bills")
    .select(
      `
      *,
      bill_contents!inner ( id, bill_id, title, summary, content,
        difficulty_level, created_at, updated_at )
    `
    )
    .eq("publish_status", "published")
    .eq("bill_contents.difficulty_level", difficultyLevel)
    .or(
      `title.ilike.%${safeQuery}%,summary.ilike.%${safeQuery}%`,
      { referencedTable: "bill_contents" }
    )
    .order("submitted_date", { ascending: false, nullsFirst: false })
    .limit(50);

  if (error) throw new Error(`Failed to search bills: ${error.message}`);
  return data;
}
```

- `bill_contents!inner` + 難易度フィルタで「現在の難易度のコンテンツがマッチした議案」のみ返す。
- `name`（議案正式名称）も検索対象に含めるかは要検討（§9）。含める場合は `bills.name.ilike` を別途 `.or()` で追加。
- 戻り値は既存の `getBills` と同様 `BillWithContent` 形へ整形する（タグの一括取得 `findTagsByBillIds` を流用）。

### 5.2 ローダー層（`search-bills.ts`）

```ts
import "server-only";

export async function searchBills(query: string): Promise<BillWithContent[]> {
  const trimmed = query.trim();
  if (trimmed.length < MIN_QUERY_LENGTH) return []; // §6.4

  const difficultyLevel = await getDifficultyLevel(); // Cookie アクセスはキャッシュ外
  const data = await findPublishedBillsBySearch(trimmed, difficultyLevel);

  const billIds = data.map((b) => b.id);
  const tagsByBillId = await findTagsByBillIds(billIds);
  return data.map((item) => toBillWithContent(item, tagsByBillId));
}
```

- **`unstable_cache` は使わない**: フリーワードはカーディナリティが高くキャッシュ効率が悪い。DB インデックス（Phase 2）で速度を担保する。
  - （[feedback_unstable_cache_shape] の教訓: もし将来キャッシュする場合、戻り値シェイプ変更時はキャッシュキーを必ずバンプする。）

## 6. 検索仕様詳細

### 6.1 対象フィールド（Phase 1）
- `bill_contents.title`（わかりやすいタイトル）
- `bill_contents.summary`（要約）
- （検討）`bills.name`（正式名称）→ §9
- 本文 `content` は Phase 1 では対象外（ノイズ・性能の懸念）。後続増分（§10.3）で検討。

### 6.2 難易度の扱い
- Cookie の現在難易度に該当する `bill_contents` のみ対象。表示中のコンテンツと検索対象を一致させ、ヒットしたのに本文が見つからない不整合を避ける。
- トレードオフ: 別難易度の文言にしか含まれない語はヒットしない。再現性を優先するなら「全難易度を対象に検索し議案単位で重複排除、表示は現在難易度」も選択肢（§9 で要確認）。

### 6.3 ソート / 件数
- ソート: `submitted_date` 降順（既存一覧と統一）。関連度ランキングは後続増分（RPC 化時）。
- 上限: 50 件（福岡市版踏襲）。超過時はページネーション（後続増分・§10.3）。

### 6.4 入力バリデーション
- `MIN_QUERY_LENGTH`（例: 2 文字）未満は検索しない（trigram 効率・ノイズ対策）。
- `trim()` 済みで空なら結果ゼロではなく「検索前」状態を表示。

### 6.5 状態別 UI
- 未検索（`q` 無し）: 説明文 + サジェストキーワード。
- ヒット 0 件: 「該当する議案が見つかりませんでした」+ 既存一覧への導線。
- ヒットあり: `BillList`（既存 `BillCard`）でカード表示。会期名・ステータス・タグは既存カードに準拠。

## 7. セキュリティ

- **フィルタ注入対策（必須）**: `sanitizeSearchQuery()` で PostgREST `or()` 構文の構造文字 `, . ( ) *` を除去してから埋め込む。福岡市版 `f70307a5` で実証済みの脆弱性を初期実装で塞ぐ。
- `ilike` のワイルドカード `% _ \` のエスケープも検討（ユーザーが `%` を入力した場合の挙動安定化）。ただし PostgREST フィルタ値内での扱いを実機検証してから決定する。
- 認可: 公開議案のみ（`publish_status='published'`）。`createAdminClient` 利用だがアプリ層で公開状態を必ず絞る。

## 8. テスト方針

- **`sanitize-search-query.ts`（純粋関数）→ テスト必須**（同階層 `.test.ts`）。構造文字除去・空入力・通常文字の保持を検証。
- **リポジトリ統合テスト**: ローカル Supabase（real）に対し `findPublishedBillsBySearch` を検証（モック禁止の規約）。既存 [bill-repository.integration.test.ts](web/src/features/bills/server/repositories/bill-repository.integration.test.ts) に倣う。
  - title 一致 / summary 一致 / 非公開（draft, coming_soon）除外 / 難易度フィルタ / 構造文字を含む入力で注入が起きないこと。
- 後続増分で RPC を導入した場合は `tests/supabase/db-function/` に統合テスト必須（規約）。

## 9. 未確定事項・要確認

> 方針: ここに挙げる多くは **「先に会議で決め打ちする」より「Phase 1 を出して §10.2 の計測値（0件ヒット率・件数・レイテンシ等）を見てから決める」方が安く正確**。アジャイルに「出して学んでから判断」する。下表の「判断材料」は、その判断に使う実データを指す。

| # | 論点 | 暫定方針 | 実データで判断する材料 |
| --- | --- | --- | --- |
| 1 | 検索対象に `bills.name`（正式名称）を含めるか | Phase 1 はタイトル・要約のみ | **0件ヒット率**が高ければ `name` 追加を検討 |
| 2 | 難易度の扱い（現在難易度のみ / 全難易度横断 + 重複排除） | 現在難易度のみ（§6.2） | 「表示中の難易度で0件だが他難易度ならヒット」する取りこぼし率 |
| 3 | 本文 `content` 検索を含めるか | Phase 1 は対象外 | 0件ヒット率・ノイズ（無関係ヒット）の体感 |
| 4 | 絞り込みフィルタ（会期・タグ・ステータス） | Phase 1 はフリーワードのみ | **1検索あたりの結果件数**が多ければ追加 |
| 5 | 検索導線の配置（ヘッダーのみ / トップにも） | ヘッダーに検索アイコン | 検索ページの流入元・利用率 |

## 10. 改良の進め方（アジャイル）

固定の「フェーズ」を積み上げるのではなく、**①最小の縦切りを出す → ②使われ方を計測する → ③シグナルに応じて独立した増分を1機能=1PRで足す**、を回す。

### 10.1 Phase 1（MVP・マイグレーション不要 / walking skeleton）

DB→リポジトリ→ローダー→ページ→UI を貫通する最小の縦切り。これ単体で「議案をキーワードで探せる」状態を出荷する。

- `sanitize-search-query.ts` + テスト
- `findPublishedBillsBySearch`（bill-repository に追加）
- `searchBills` ローダー
- `/search/page.tsx` + `SearchBox` + `SearchResults`
- `routes.search()` 追加 + routes.test 同期
- ヘッダーに検索導線
- リポジトリ統合テスト
- **計測の仕込み（§10.2）**

### 10.2 計測（次の一手を決めるためのフィードバックループ）

Phase 1 出荷時に以下を観測できるようにする（既存の分析基盤に合わせて実装。最低限ログでも可）。これが無いと「次に何を作るか」を勘で決めることになる。

| 指標 | 何が分かるか |
| --- | --- |
| 検索ページの利用率・流入元 | そもそも検索が使われているか、導線が適切か |
| **0件ヒット率** | 言葉が一致せず探せていない度合い（最重要） |
| **1検索あたりの結果件数** | 絞り込みが必要かどうか |
| **検索レイテンシ** | seq スキャンが重くなっていないか |
| クエリ文字数分布 | 最小文字数・サジェストの調整材料 |

### 10.3 シグナル駆動バックログ（順序固定ではない）

計測値の悪化をトリガーに、独立した増分として投入する。各項目は単独で出荷可能・優先順位は実データで入れ替える。

| トリガーとなるシグナル | 投入する増分（独立PR） |
| --- | --- |
| 0件ヒット率が高い | `name` 検索追加 → 本文 `content` 検索 → （最終手段）AI セマンティック検索 |
| 検索レイテンシ悪化 | pg_trgm GIN インデックス（マイグレーションのみ・アプリ改修不要） |
