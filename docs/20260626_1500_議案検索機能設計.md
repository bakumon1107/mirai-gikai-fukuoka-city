# 議案検索機能 設計書

- 作成日: 2026-06-26 / 最終更新: 2026-07-12（実装反映）
- 対象アプリ: `web/`（公開サイト）
- ステータス: **実装済み**（§5〜§8 は実装の記述、§9〜§10 は今後の改良方針）

## 1. 背景・課題

公開サイトはトップページで議案（bills）を **タグ別・注目・会期別** に並べて表示しているが、フリーワードでの検索ボックスが存在しなかった。会期（diet_sessions）が増え、過去会期も含めた掲載議案数が増加してきたため、「特定のキーワードを含む議案を探す」導線が必要になった。

従来の議案発見手段（タグ別セクション・注目・前回会期・会期別ページ）はいずれも「カテゴリで絞る」操作であり、横断的なフリーワード検索ができなかった。

## 2. 目的・スコープ

### 目的
掲載済み（`publish_status = 'published'`）の議案を、タイトル・要約のフリーワードと絞り込み条件で横断検索できるようにする。

### 実装済みスコープ
- `/search` ページ（検索フォーム・絞り込みフィルタ4種・結果一覧・ページネーション・0件時の救済）
- ヘッダー全ページへの検索導線
- 表記ゆれ吸収（かな・NFKC）と難易度またぎマッチ
- 入力サニタイズ等のセキュリティ対策

### スコープ外（将来課題・§10）
本文（`content`）検索、関連度ランキング、ハイライト表示、サジェスト、AIセマンティック検索、検索ログ分析。

## 3. 前提調査

### 3.1 データモデル

| テーブル | 検索に関わるカラム | 備考 |
| --- | --- | --- |
| `bills` | `status`, `submitted_date`, `diet_session_id`, `publish_status` | 公開判定は `publish_status='published'` |
| `bill_contents` | `title`（わかりやすいタイトル）, `summary`（要約）, `content`（本文） | `bill_id` × `difficulty_level` で複数行 |
| `bills_tags` / `tags` | `tags.label`, `featured_priority` | カテゴリフィルタの選択肢 |
| `diet_sessions` | `name`, `start_date` | 会期フィルタの選択肢 |
| `interview_configs` | `status` | 「AIインタビュー受付中」フィルタ（`status='public'`） |

- 公開サイトは Cookie 由来の難易度（`getDifficultyLevel()`）で表示する `bill_contents` を選ぶ。
- データアクセスは全て `createAdminClient()` 経由。RLSは有効・ポリシー無し（デフォルト全拒否）、認可はアプリ層（AGENTS.md 準拠）。

### 3.2 先行事例（姉妹フォーク fukuoka-city）

福岡市版フォークに `features/search/`（PostgREST `.or(ilike)` 方式・タブ型）の実装があり、方式選定の参考にした。特に同フォークの修正コミットで実証された **PostgREST `or()` フィルタへの条件注入**（`a,id.neq.0` のような入力で意図しないフィルタが注入される）の知見を、本実装では初期から対策に織り込んだ（§7）。

## 4. 設計方針：検索方式の選定

日本語は語境界（スペース）が無いため、PostgreSQL 標準の `to_tsvector` は素の状態では使えない。

| 方式 | 日本語対応 | Supabase Hosted | 実装コスト | 採否 |
| --- | --- | --- | --- | --- |
| **PostgREST `.or(ilike '%q%')`** | ◎（部分一致なので分かち書き不要） | ○ | 低（マイグレ不要） | **採用** |
| pg_trgm GIN インデックス + ilike | ◎ | ○（拡張利用可） | 中（マイグレ要） | 性能劣化時の後続増分（§10.2） |
| PGroonga / pg_bigm | ◎（最良） | ×（hosted 非対応） | 高 | 不採用 |
| tsvector + 独自 bigram 分割 | △ | ○ | 高（保守重） | 不採用 |
| AI ベクトル検索（embeddings） | ◎（意味検索） | ○（pgvector） | 高 | 将来構想（§10.3） |

採用理由: 部分一致は分かち書き不要で、現データ規模（数十〜数百件）では追加インデックス無しでも十分高速。マイグレーション不要で最短で価値提供でき、`ilike` はそのまま pg_trgm インデックスで加速できるため、増加後の性能対策もアプリ側の変更なしで打てる。関連度ランキングや複合条件が必要になった段階で初めて RPC（DB function）+ 統合テストへ移行する。

### 5.1 検索クエリの流れ（2段クエリ）

```
入力 q
 └→ normalizeSearchQuery（NFKC + trim）
     └→ buildSearchQueryVariants（原文/ひらがな化/カタカナ化 の重複排除）
         └→ 各変種を sanitizeSearchQuery（構造文字除去・最大長100）+ escapeIlikePattern（% _ \）
             └→ [1段目] bill_contents を難易度を問わず or(title.ilike, summary.ilike×変種) 検索 → bill_id 集合
                 └→ [2段目] bills + 現在難易度の bill_contents!inner を
                            id in (マッチ集合) + publish_status='published' + 各フィルタで取得
```

- **難易度またぎ**: マッチ判定は全難易度、表示は現在難易度。「やさしい」表示中でも「詳しい」版にしか無い語で取りこぼさない。
- **表記ゆれ吸収**: 「すとーかー」「ｽﾄｰｶｰ」→「ストーカー」。DB側の正規化カラム不要（アプリ側でクエリを最大3変種に展開）。
- タグ・AIインタビューの絞り込みも対象 `bill_id` を先に解決して `.in()`（select文字列の動的組み立てを避け型推論を保つ）。
- クエリもフィルタも無い場合は**全公開議案の一覧**として機能（空エンター・初回表示で行き止まりにしない）。
- ソートは `submitted_date` 降順。**ページネーション**は `SEARCH_PAGE_SIZE`（20件/ページ）で `range()` + `count: "exact"` を同一リクエストで取得（オフセット方式。件数表示は総ヒット数）。範囲外ページ（URL直打ち・結果数の変動）は PostgREST が 416 を返すため、リポジトリで `count: null` に変換し、ローダーが最終ページへ丸めて取り直す。
- `unstable_cache` は不使用（フリーワードはカーディナリティが高くキャッシュ効率が悪い）。Cookie（難易度）はキャッシュ外で解決。

### 5.2 絞り込みフィルタ

| フィルタ | URLパラメータ | 値 | 選択肢の取得元 |
| --- | --- | --- | --- |
| 国会会期 | `session` | `diet_sessions.id` | `findAllDietSessions()`（開始日降順） |
| カテゴリ | `tag` | `tags.id` | `findFeaturedTags()`（既存流用） |
| ステータス | `status` | 下表のフィルタ値 | `STATUS_FILTER_OPTIONS` 定数 |
| AIインタビュー | `interview` | `"1"` | `interview_configs.status='public'`（カードのバッジと同一条件） |
| ページ | `page` | 1始まりの整数（1は省略） | — |

ステータスは表示ラベルが議院に依存する2値を「審議中」に集約する:

| フィルタ値 | ラベル | 対象 status |
| --- | --- | --- |
| `deliberating` | 審議中 | `in_originating_house`, `in_receiving_house` |
| `enacted` / `rejected` / `introduced` / `preparing` | 成立 / 否決 / 提出済み / 準備中 | 同名 enum |

`resolveStatusFilter()` は未知の値（URL改ざん）を null＝フィルタなしとして扱う。テストで「全 enum がいずれかの選択肢でカバーされている」ことを検証し、enum 追加時の漏れを検出する。

フィルタ状態は URL と1:1（共有・リロード可能）。キーワード変更時もフィルタは維持され、「絞り込みを解除」でフィルタのみリセットされる。キーワード・フィルタを変更した場合はページが1に戻る（`page` を引き継がない）。

### 5.3 状態別 UI（search-results.tsx）

| 状態 | 表示 |
| --- | --- |
| 条件なし | 全公開議案「すべての議案: N件」 |
| キーワード検索 | 「『q』の検索結果: N件」+ 既存 `BillList`（BillCard再利用） |
| フィルタのみ | 「絞り込み結果: N件」 |
| 入力が短すぎ（サニタイズ後 < 2文字）かつフィルタなし | 「キーワードは2文字以上で入力してください」 |
| **0件** | 行き止まりにしない: ①フィルタ指定時はフィルタなしで再検索し「絞り込みを解除するとN件見つかります」リンク ②提案キーワードのチップ |
| 複数ページ | 一覧下部にページ送りナビ（前後リンク＋番号。先頭末尾＋現在±1を表示し間は省略記号。現在ページは `aria-current="page"`） |

### 5.4 0件時のAIチャット橋渡し（実装済み→保留）

0件時に既存 `ChatButton` の `openWithText()` ref を再利用し、「AIチャットで『{q}』について聞いてみる」ボタンで**検索語をそのままチャットへ引き継ぐ** `SearchChatBridge`（client）を一度実装した。キーワード一致では拾えない曖昧な質問（「年金って結局どうなるの？」等）を既存チャット資産で救済でき、セマンティック検索導入前の安価な代替になる。

ただし、検索起点のチャット流入が増えるとAIコスト（AI Gateway 課金）に直結するため、**リリース判断としていったん封印（コードは削除）**した。復元する場合は次を再実装する:

- `bill-search/client/components/search-chat-bridge.tsx`（ChatButton の ref 保持＋トリガーボタン。検索結果の議案リストをチャットコンテキストとして渡す）
- `/search/page.tsx` からの呼び出し（0件かつ有効キーワードかつ緩和ヒント無しのとき `noHitQuery` を渡す）

再開の判断材料は、検索の利用量・0件ヒット率（§10.1）とチャットの日次コスト上限の余裕。

### 5.5 ルート・導線

- `routes.search(q?, filters?)` を追加（routes.test.ts の page.tsx 同期検証を通過）。
- ヘッダーに検索アイコンを**全ページで常時表示**。検索結果は難易度Cookieに依存するため、`/search` では難易度セレクタも表示する。

## 6. 入力処理の詳細

- **最小文字数**: サニタイズ後2文字未満は検索しない（構造文字だけの水増し入力を弾く）。空入力は全件一覧として有効。
- **searchParams の型**: 同名パラメータ重複で `string[]` が渡るため、全パラメータを `typeof === "string"` ガードで受ける（`?q=a&q=b` でのクラッシュ防止）。
- **正規化**: NFKC で全角英数・半角カナを標準化。かな相互変換はコードポイント ±0x60 の純粋関数。

## 7. セキュリティ（実装済み対策）

| 脅威 | 対策 |
| --- | --- |
| PostgREST `or()` への条件注入 | `sanitizeSearchQuery()` が構造文字 `, . ( ) * "` を除去（引用符はクォート値解釈によるパースエラー防止） |
| ILIKE ワイルドカード悪用（`%%` で全件・最小文字数バイパス、末尾 `\` でパターン破壊） | `escapeIlikePattern()` が `% _ \` をエスケープ（埋め込み直前に1回だけ適用。冪等でないため） |
| 長大入力による DB 負荷・URL 肥大 | 最大長100文字で切り詰め（かな変換で最大3倍に展開されるため特に重要） |
| XSS | ユーザー入力の echo は JSX 経由（React が自動エスケープ）。`dangerouslySetInnerHTML` 不使用。URL 生成は `encodeURIComponent` / `URLSearchParams` |
| 非公開議案の漏洩 | 1段目のマッチは bill_id の収集のみに使い、返却データは必ず `publish_status='published'` で絞る |
| フィルタ値の注入 | id 系は `.eq()`（クライアントがエンコード）、status/interview は許可リストで解決 |

## 9. 積み残し（実装時に見送った論点）

1. **`bills.name`（正式名称）の検索対象化** — 固有名詞検索に有効だが、0件ヒット率の実測を見てから（§10.1）。
2. **本文 `content` 検索** — 再現性↑ / ノイズ・性能↓。同じく実測後に判断。
3. 関連度ランキング、ハイライト。
4. **0件時のAIチャット橋渡し**（§5.4）— コスト判断で封印中。

## 10. 改良の進め方（アジャイル）

固定のフェーズを積み上げるのではなく、**①最小の縦切りを出す → ②使われ方を計測する → ③シグナルに応じて独立した増分を1機能=1PRで足す**、を回す。①は本設計書のスコープとして実装済み。

### 10.1 計測（次の一手を決めるためのフィードバックループ）

以下を観測できるようにする（既存の分析基盤に合わせて実装。最低限ログでも可）。これが無いと「次に何を作るか」を勘で決めることになる。

| 指標 | 何が分かるか |
| --- | --- |
| 検索ページの利用率・流入元 | そもそも検索が使われているか、導線が適切か |
| **0件ヒット率** | 言葉が一致せず探せていない度合い（最重要） |
| **1検索あたりの結果件数** | 絞り込み・ページネーションの要否 |
| **検索レイテンシ** | seq スキャンが重くなっていないか |
| クエリ文字数分布 | 最小文字数・サジェストの調整材料 |

### 10.2 シグナル駆動バックログ（順序固定ではない）

| トリガーとなるシグナル | 投入する増分（独立PR） |
| --- | --- |
| 0件ヒット率が高い | `name` 検索追加 → 本文 `content` 検索 → 同義語辞書 → チャット橋渡し復元（§5.4） → （最終手段）AI セマンティック検索 |
| 検索レイテンシ悪化 | pg_trgm GIN インデックス（マイグレーションのみ・アプリ改修不要） |
| 1検索あたり件数が多い | ファセット件数表示（選択肢に件数を添える） |
| 「なぜヒットしたか分からない」フィードバック | 検索結果ハイライト・マッチ箇所スニペット |
| 関連度順が欲しい要望 | 関連度ランキング（RPC + `tests/supabase/db-function/` 統合テストへ移行） |

### 10.3 将来構想（実利用データが十分に溜まってから判断）

- **pgvector による AI セマンティック検索**: 「待機児童」→「保育所の定員拡充」のような言い換え・同義語でもヒットさせる（文字列一致では取りこぼす領域）。
- **トピック（みんなの意見）の検索対象化**: 議案/トピックのタブ型検索。AI生成テキストのためノイズ設計（公開版のみ等）を検討してから。
- サジェスト / 人気キーワード / 検索ログ分析。
