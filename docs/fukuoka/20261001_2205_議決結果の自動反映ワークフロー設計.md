# 議決結果の自動反映ワークフロー設計

作成日: 2026-10-01

---

## 1. 概要

福岡市議会公式サイトに議決結果が掲載されたら、GitHub Actions が自動で `bills.status` / `bills.status_note` / `bills.decided_date` / `faction_stances` を更新する。

### なぜ自動化できるのか

議案データの取込は、これまで手作業（都度のスクレイピングとDB操作）で行ってきた。この作業を工程ごとに分解すると、**AIの判断が必要なのは「AI解説（bill_contents）の執筆」だけ**で、議決結果の反映にはAIの判断が一切含まれない。

| 工程 | 内容 | 自動化 |
|---|---|---|
| 更新の検知 | RSSの差分確認 | 可 |
| 会期ページのパース | 議案番号・議決年月日・議決結果・会派別採決の抽出 | 可 |
| 値の変換 | 「可決」→`approved`、「○」→`for` 等の対応表引き | 可 |
| DB反映 | Supabase REST への PATCH / POST | 可 |
| キャッシュ無効化 | `/api/revalidate` への POST | 可 |
| AI解説の執筆 | 議案PDFを読んで市民向けに書く | **不可（本設計のスコープ外）** |

したがって本ワークフローは **LLMを一切呼ばない**。Claude Code CLI も Anthropic API も不要で、Node.js スクリプトと GitHub Actions だけで完結する。

### 解決したい課題

- 議決後、公式サイトに結果が載ったことに気づくまで時間がかかる（現状は手動で会期ページを見に行っている）
- 反映作業そのものは定型で、会期ごとに同じ手順を繰り返している
- 2026-10-01時点で、r8-4（令和8年第4回）の9月10日議決分が未反映のまま残っている

---

## 2. スコープ

### やること

- 公式サイトの更新検知（RSS）
- 会期ページのパースと、DBとの突合
- **既にDBに存在する議案**の `status` / `status_note` / `decided_date` / `faction_stances` の更新
- 反映結果の通知（GitHub Issue）
- 想定外データ検出時の安全な停止

### やらないこと（本設計のスコープ外）

- **AI解説（bill_contents）の生成** — LLMが必要。従来どおり人間（Claude Code セッション）が行う
- **新規議案レコードの作成** — 会期途中に提出される意見書案・決議案・請願は、議決と同時に公式サイトへ現れる。これらはDBに行が無く、AI解説もセットで必要になるため、**自動作成せず通知のみ**とする
- 同意案・人事案件の取込（従来どおり対象外。[docs/fukuoka/20260329_1000_福岡市議会データ取込設計.md](20260329_1000_福岡市議会データ取込設計.md) の方針を踏襲）
- 委員会議事録・一般質問・市長記者会見の取込（別スクリプト群が既にある）

---

## 3. 全体の流れ

```
[GitHub Actions / cron]
        |
        | (1) RSS を条件付きGET（ETag）
        ↓
   変化なし → 終了（APIもDBも叩かない）
        |
        | (2) 現会期の会期ページを取得・パース
        ↓
   [公式データ: 議案番号 → 議決日・議決結果・会派別採決]
        |
        | (3) DBの現会期 bills と突合
        ↓
   差分なし → 終了
        |
        | (4) 想定外データの検査
        ↓
   未知の議決結果／未知の会派ラベル → 書き込まず Issue を立てて停止
        |
        | (5) DB更新（status / status_note / decided_date / faction_stances）
        ↓
        | (6) /api/revalidate で web のキャッシュ無効化
        ↓
        | (7) 反映件数を Issue にコメント
```

### 状態を持たない設計にする

「どこまで処理したか」をファイルやキャッシュに記録する方式は、取りこぼしや二重適用の原因になる。本ワークフローは**状態を持たず、毎回「公式ページの現在値」と「DBの現在値」を突合して差分だけを適用する**。

- 同じ回を何度実行しても結果が変わらない（冪等）
- 一度失敗しても次回実行で自動的に復旧する
- RSSはあくまで「DBアクセスを省くための前段フィルタ」であり、判定の根拠にはしない

## 4. 検知仕様（RSS）

### フィード

| 項目 | 値 |
|---|---|
| URL | `https://gikai.city.fukuoka.lg.jp/feed/` |
| 形式 | RSS 2.0（`/feed/atom/` で Atom も可） |
| 件数 | 1ページ10件。`?paged=N` で遡れる |
| 条件付きGET | `ETag` と `Last-Modified` を返すため利用可能 |
| カテゴリ | 全件「分類なし」。カテゴリ別フィードでの絞り込みは不可 |

### 検知する文言

お知らせのタイトルは定型文で安定している。

| 種別 | タイトル例 |
|---|---|
| 新会期の議案公開 | `議案・会議結果に令和8年第4回福岡市議会（9月定例会）の議案を掲載しました。` |
| 議決結果の掲載 | `議案・会議結果に令和8年第4回福岡市議会（9月定例会）の会議結果を掲載しました。（9月10日議決分）` |

本ワークフローは **`議案・会議結果に` を含み、かつ `会議結果` を含む** item を検知対象とする。

### 条件付きGETの扱い

`ETag` を Actions のキャッシュ（`actions/cache`）に保存し、次回は `If-None-Match` を付けて取得する。`304 Not Modified` なら即終了する。

これは**サイトへの負荷を下げるための最適化であり、処理の正しさには関与しない**。キャッシュが消えても、フィードの文言が変わっても、後続の突合処理が正しく差分を検出する。

> 注: 会期ページ（`/result/r8_gikai4/`）自体は `Last-Modified` も `ETag` も返さないため、ポーリング対象はRSSとする。

## 5. パース仕様（会期ページ）

### URL

`https://gikai.city.fukuoka.lg.jp/result/r{令和年}_gikai{回}/`

例: 令和8年第4回 → `https://gikai.city.fukuoka.lg.jp/result/r8_gikai4/`

DBの `council_sessions.council_url` に同じURLを保持しているため、**処理対象の会期は `is_active = true` の会期**とし、その `council_url` を使う。

### テーブル構造

TablePress 製のテーブルで、**行が属性・列が議案**という転置構造になっている。

```
議案番号      | 157      | 158      | ...
提出年月日    | R8.9.2   | R8.9.2   | ...
件名          | 令和７年度福岡市一般会計歳入歳出決算 | ... 
議決年月日    | R8.9.10  | R8.9.10  | ...
議決結果      | 認定     | 認定     | ...
自民          | ○        | ○        | ...
公明          | ○        | ○        | ...
（会派が続く）
```

1ページに複数のテーブルが並ぶ（市長提出議案・議員提出議案・意見書案・決議案・請願）。

### 議案種別の判定

**1行目のラベルだけでは種別を判定できない。** 実例:

- 市長提出議案のラベルが `議案番号` のことも、**空文字**のこともある（r7-4 は空文字）
- 議員提出議案のラベルも `議案番号`（市長提出議案と同じ）

そのため、**テーブルの直前に現れる見出しテキスト**で判定する。

| 直前の見出し | `bill_number` の形式 |
|---|---|
| `〔市長提出議案〕` | `第{N}号` |
| `〔議員提出議案〕` | `議員提出議案第{N}号` |
| `〔意見書案〕` | `意見書案第{N}号` |
| `〔決議案〕` | `決議案第{N}号` |
| `請願` | `請願{N}` |

見出しが特定できないテーブルは**処理せず警告する**（勝手に推測しない）。

### 正規化

- **全角・半角の揺れ**: 議案番号が `第１号`（全角）の会期がある。会派ラベルも `無所属１`（全角）と `無所属1`（半角）が混在する。`unicodedata.normalize("NFKC", s)` 相当で正規化してから突合する
- **和暦の変換**: `R8.9.2` → `2026-09-02`（西暦 = 2018 + 令和年）。パターンに合わない値は変換せず警告する
- **空欄**: 議決前は議決年月日・議決結果・会派別採決がすべて空欄。空欄の列は更新対象から外す

### 会派列の順序は会期ごとに変わる

r8-4 は `自民 / 公明 / 市民ク / 共産 / 新風 / 維新 / 自民新`、r7-4 は `自民 / 公明 / 市民ク / 維新 / 共産 / 自民新 / 新風` と**順序が異なる**。列位置ではなく**必ずラベルで引く**こと。

## 6. 変換仕様

### 議決結果 → status

| 公式サイトの議決結果 | `status` | `status_note` |
|---|---|---|
| 可決 | `approved` | null |
| 承認 | `approved` | `承認` |
| 認定 | `approved` | `認定` |
| 採択 | `approved` | `採択` |
| 否決 | `rejected` | null |
| 不採択 | `rejected` | null |
| 継続審査 | `in_committee` | `継続審査` |
| 同意 | **対象外**（人事案件。DBに登録しない） | — |
| 上記以外 | **停止してIssue** | — |

> **実装上の注意**: 「不採択」の判定を「採択」より**先**に行うこと。部分一致で判定すると「不採択」が `採択` にマッチして `approved` になるバグが過去に発生している（[.claude/skills/update-bills/SKILL.md](../../.claude/skills/update-bills/SKILL.md) 参照）。

`status_order` と `publish_status_order` は GENERATED カラムのため**設定しない**。

### 会派ラベル → faction_id

| ラベル | `factions.name` |
|---|---|
| 自民 | `jimin-fukuoka` |
| 公明 | `komei` |
| 市民ク | `fukuoka-shimin` |
| 共産 | `kyosan` |
| 新風 | `atarashii-kaze` |
| 維新 | `ishin` |
| 自民新 | `jimin-shin-fukuoka` |
| 無所属１ | あべ ひでき |
| 無所属２ | 新開 ゆうじ |
| 無所属３ | 木村 てつあき |
| 無所属４ | 森 あやこ |
| 無所属５ | 川口 浩 |

**無所属Nは汎用の「無所属」レコードではなく議員個人のレコードを使う。** 順序は公式サイトの議員名簿（会派別）の議席番号順。

> **改選・会派異動のリスク**: このマッピングは議員構成が変わると破綻する。マッピングはコード内にハードコードせず**設定ファイル（JSON）として持ち**、未知のラベルが出たら停止する。会期の初回反映時には人間が公式の会派構成と突合する運用を維持する。

### 賛否記号 → stance type

| 記号 | `faction_stances.type` |
|---|---|
| ○ | `for` |
| × | `against` |
| 空欄 | レコードを作らない |

## 7. 反映仕様

### 突合キー

`(council_session_id, bill_number)` で突合する。`bill_number` は NFKC 正規化し空白を除去して比較する。

**表記揺れの実例**: r7-5 の議員提出議案は、公式サイトでは `議員提出議案第4号`、DBでは `第4号`（`bill_type = member_bill`）として登録されていた。自動突合から漏れるため、**漏れた議案は黙って無視せず一覧をIssueに出す**。

### 更新内容

公式サイトに議決結果がある議案のうち、DBの値と異なるものだけを更新する。

```
status        ← 対応表による変換結果
status_note   ← 対応表による変換結果
decided_date  ← 議決年月日（YYYY-MM-DD）
```

`faction_stances` は**差分更新ではなく全置換**する（議案単位で DELETE → INSERT）。部分的な更新は重複や取りこぼしを生むため。

### DBに無い議案の扱い

公式サイトにあってDBに無い議案は、次の3通りが考えられる。**いずれも自動では作らず、Issueに一覧を出す。**

| ケース | 対応 |
|---|---|
| 同意案・人事案件 | 正常。方針どおり取り込まない（Issueには「対象外」として記載） |
| 新規の意見書案・決議案・請願 | **AI解説が必要**なので人間の作業に回す |
| 取込漏れ | 人間が確認する |

## 8. ガードレール

**壊れたデータを書き込むより、止まって知らせるほうが望ましい。** 以下のいずれかに該当したら、DBへ一切書き込まずIssueを立てて異常終了する。

1. 未知の議決結果の文字列が現れた
2. 未知の会派ラベルが現れた（改選・新会派結成の可能性）
3. 会期ページのテーブルの種別が判定できない
4. 和暦の日付がパターンに合わない
5. `is_active = true` の会期が0件、または2件以上
6. 会派別採決の件数が `対象議案数 × 会派数` と一致しない
7. 1回の実行で更新対象が異常に多い（**しきい値: 100議案**。通常の会期は50件程度）

### dry-run モード

`workflow_dispatch` の入力で `dry_run: true` を指定した場合、DBへ書き込まず「何件をどう更新するか」だけをIssue（またはジョブサマリ）に出力する。新会期の初回はこれで内容を確認してから本実行する運用を推奨する。

## 9. GitHub Actions の設計

### トリガ

```yaml
on:
  schedule:
    - cron: "0 1,4,7,10 * * 1-5"   # JST 10:00 / 13:00 / 16:00 / 19:00（平日）
  workflow_dispatch:
    inputs:
      dry_run:
        type: boolean
        default: true
```

- `pull_request` では**絶対に動かさない**（Secretsを扱うため）
- 本会議の採決は平日の日中に行われ、掲載は数日以内。高頻度のポーリングは不要
- GitHubのcronは数分〜十数分遅れることがある。即時性は要求しない
- 公開リポジトリは60日間コミットが無いとスケジュールが停止する（本リポジトリは活発なため実害なし）

### 権限と Secrets

```yaml
permissions:
  contents: read
  issues: write
```

| Secret | 用途 |
|---|---|
| `SUPABASE_URL` | 本番Supabase REST のベースURL |
| `SUPABASE_SERVICE_ROLE_KEY` | bills / faction_stances の読み書き |
| `WEB_URL` | revalidate 先 |
| `REVALIDATE_SECRET` | `/api/revalidate` の Bearer トークン |

> **このリポジトリは public である。** 現在登録済みのSecretは `WEB_VERCEL_DEPLOY_HOOK_URL` のみで、本ワークフローで初めて本番DBの書き込み権限をCIに渡すことになる。フォークからのPRにSecretsは渡らないが、ワークフローファイルを変更できる権限を持つ者は値を持ち出せる。トリガを `schedule` / `workflow_dispatch` に限定することと、ログに値を出さないことを徹底する。

### サイトへの配慮

- User-Agent を明示する
- リクエスト間隔は1〜2秒
- 1回の実行で取得するのはRSS1回＋会期ページ1回（PDFは取得しない）

## 10. 実装構成

```
packages/seed/fukuoka/
├── parse-result-page.ts        # 会期ページHTML → 構造化データ（純粋関数）
├── parse-result-page.test.ts
├── map-vote-result.ts          # 議決結果・賛否記号の変換（純粋関数）
├── map-vote-result.test.ts
├── factions-map.json           # 会派ラベル → faction name のマッピング
└── apply-vote-results.ts       # 突合・DB反映・revalidate（I/O担当）

.github/workflows/
└── sync_vote_results.yml
```

- HTMLパースと値の変換は**外部依存を持たない純粋関数**として切り出し、`*.test.ts` を必ず書く（[CLAUDE.md](../../CLAUDE.md) の方針）
- テストには実際の会期ページHTML（r8-4・r7-4・r8-1）を固定データとして持たせる。会派列の順序違い、全角番号、空欄、種別の見出し判定といった実例を回帰テストにする
- DBアクセスを伴う `apply-vote-results.ts` は、ローカルSupabaseに対する結合テストで検証する

## 12. 未決事項（判断が必要）

1. **本番DBの書き込み権限をCIに渡すことの可否**
   public リポジトリに `SUPABASE_SERVICE_ROLE_KEY` を置くことになる。抵抗がある場合の代替案:
   - (a) CIは検知とパースのみ行い、**反映用のSQLを生成してIssueに貼る**（人間が実行）
   - (b) 書き込み専用の限定ロール／Edge Function を用意し、CIにはそれだけを渡す

2. **「採択」「継続審査」のマッピング**
   `bill_status_enum` には `adopted` / `partially_adopted` が存在するが、現在DBでの使用実績が無い。請願の「採択」を `approved` とするか `adopted` とするかを決める必要がある。本設計では暫定的に `approved` + `status_note` としている。

3. **通知先**
   Issueで足りるか、別の通知（Slack等）が要るか。

4. **決算議案の「認定」バッジ表示**
   `approved` にマップするため画面では「可決」バッジに `認定` の補足が並ぶ。決算専用の表示が必要かどうか。
