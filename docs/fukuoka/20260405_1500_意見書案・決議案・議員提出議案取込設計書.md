# 意見書案・決議案・議員提出議案 取込設計書

作成日: 2026-04-05

## 背景と目的

現在、採決結果ページ（`https://gikai.city.fukuoka.lg.jp/result/r8_gikai1/` 等）には通常の議案（首長提出）のほか、以下の議案種別が掲載されているが、DBへの取込が行われていない。

- **意見書案**（議員が国・都道府県へ意見を述べる議案）
- **決議案**（議会内部の意思を表す決議）
- **議員提出議案**（議員が直接提出する条例案等）

これらを取り込むことで、市民が会議の全体像を把握できるようになる。

## 議案種別の定義

| 種別 | bill_type 値 | 議案番号プレフィックス例 |
|---|---|---|
| 通常議案（首長提出） | `bill` | 第1号〜第122号 |
| 意見書案 | `opinion` | 意見書案第1号 |
| 決議案 | `resolution` | 決議案第1号 |
| 議員提出議案 | `member_bill` | 第4号（注記で識別） |

## 実装方針

### Phase 1: DBスキーマ拡張

#### `bills` テーブルに `bill_type` カラムを追加

```sql
ALTER TABLE bills ADD COLUMN bill_type text NOT NULL DEFAULT 'bill'
  CHECK (bill_type IN ('bill', 'opinion', 'member_bill', 'resolution'));
```

マイグレーション作成 → `packages/supabase/types` を再生成。

### Phase 2: スクレイピングスクリプト拡張（master-data リポジトリ）

`packages/seed/fukuoka/` に以下を追加・修正：

#### `scrape-votes.ts`（新規）

公式サイトから全テーブルを解析し、議案種別ごとにデータを返す共通スクレイパー。

```typescript
type VoteTable = {
  billType: 'bill' | 'opinion' | 'resolution' | 'member_bill';
  bills: ScrapedBill[];
};

type ScrapedBill = {
  number: string;        // "1", "2", "11" 等
  title: string;
  sourceUrl: string | null;
  submittedDate: string;
  decidedDate: string;
  result: '可決' | '否決' | '承認' | '同意';
  votes: Record<string, '○' | '×'>;  // 会派名 → 賛否
};

function scrapeVotePage(html: string): VoteTable[];
```

**テーブル種別の判定ロジック：**
1. 先頭ラベルが `意見書案番号` → `opinion`
2. 先頭ラベルが `決議案番号` → `resolution`
3. 先頭ラベルが `議案番号` かつ直前に `〔議員提出議案〕` の注記 → `member_bill`
4. それ以外 → `bill`

#### `import-special-bills.ts`（新規）

スクレイパーの結果を使ってDB（cloud Supabase）に投入するスクリプト。

```bash
# 実行例
tsx packages/seed/fukuoka/import-special-bills.ts \
  --url https://gikai.city.fukuoka.lg.jp/result/r8_gikai1/ \
  --session-id <council_session_id> \
  --dry-run
```

**処理フロー：**
1. 指定URLをフェッチ
2. `scrapeVotePage()` で全テーブル解析
3. `bill_type` が `bill` 以外のものを対象に処理
4. `bills` テーブルに INSERT（`bill_type`・`bill_number`・`name`・`source_url`・`status`・`publish_status: 'published'`）
5. `faction_stances` テーブルに INSERT（無所属は個人単位）
6. `bill_contents` は空のまま作成（後でAI生成 or 手動入力）

### Phase 3: Admin UI 対応

#### Bills 一覧での表示

`bill_type` に応じてバッジを表示：

```
[議案] [意見書案] [決議案] [議員提出]
```

フィルターにも `bill_type` を追加。

#### Web 表示

議案詳細ページのタイトル下に種別バッジを表示（任意）。

## 考慮事項

### 件名のURL（source_url）

- **通常議案**: PDFへの直接リンク（`/wp-content/uploads/.../gianXX.pdf`）
- **意見書案**: PDFへのリンク（`iken_XXXX.pdf`）
- **決議案**: PDFへのリンク（`ketsugi_XXXX.pdf`）
- **議員提出議案**: PDFまたは市公式サイトのHTMLページ

→ `source_url` に格納、Web側の「議案原文」リンクとして表示。

### bill_number の衝突問題

意見書案と通常議案で `第1号` が重複する。`council_session_id` + `bill_number` + `bill_type` で一意とする。

```sql
-- 既存ユニーク制約がある場合は変更が必要
-- 現状: council_session_id + bill_number のみ
-- 変更: council_session_id + bill_number + bill_type
```

→ マイグレーションで制約を変更する。

### 意見書案・決議案のコンテンツ生成

PDFをダウンロードしてAIでサマリーを生成し、`bill_contents` に格納する。

**生成フロー：**
1. `source_url`（PDF）をダウンロード
2. Claude API でテキスト抽出 → 市民向けにわかりやすく変換
3. `normal`（やさしい）/ `hard`（詳しい）の2種類を生成
4. `publish_status: 'published'` で直接公開

→ AI収集の既存フロー（`enrichBillContents`）を流用する。

## 残課題

### bill_number の衝突問題（要スキーマ変更）

同じ会期に「通常議案 第1号」と「意見書案 第1号」が共存するため、DBの一意制約が衝突する。

**現在の制約:** `(council_session_id, bill_number)` が UNIQUE

**変更後:** `(council_session_id, bill_number, bill_type)` を UNIQUE に変更

```sql
-- 既存制約を削除して再作成
ALTER TABLE bills DROP CONSTRAINT IF EXISTS bills_council_session_id_bill_number_key;
ALTER TABLE bills ADD CONSTRAINT bills_session_number_type_key
  UNIQUE (council_session_id, bill_number, bill_type);
```

マイグレーションファイルとして作成し、型定義も再生成する。

### 無所属議員マッピングの会期ごとの差異

- **r8_gikai1**（令和8年第1回）: 無所属１〜５ → 個人名マッピング済み
- **r7_gikai5 以前**: 無所属の人数・構成が異なる → **無所属１〜n のまま登録**（個人名マッピングなし）

スクレイパーが無所属Nを検出した場合、該当する faction が DB に存在しなければそのまま `display_name: "無所属N"` で faction を作成する。
