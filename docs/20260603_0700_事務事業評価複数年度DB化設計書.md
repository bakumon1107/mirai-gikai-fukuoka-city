#### 🔍 現在の問題点
1. **JSON分散管理**: データがJSONファイルとして分散し、クエリが困難
2. **複数年度の重複**: R5→R6で同一事業の追跡が手動依存
3. **スケーラビリティ**: 新年度追加時にファイル追加が必要
4. **検索・分析の制限**: DBなしのため「全部局の同一事業の推移」の抽出が困難
5. **歴年データ欠落**: R2～R4のデータが未取込

## 2. 要件定義

### 2.1 機能要件

| 要件 ID | 要件名 | 説明 |
|--------|------|------|
| FR1 | 複数年度の一元管理 | R2～R6（5年間）のデータをDBで統合管理 |
| FR2 | 同一事業の自動追跡 | 事業名・所管局・所管課から同一事業を判定し、年度別レコードでリンク |

## 3. DBスキーマ設計

### 3.1 テーブル概要

```
jimu_jigyo_items (基本情報)
  ├─ 事業マスタ（事業名、所管局、所管課、開始年度等）
  
jimu_jigyo_fiscal_years (年度別データ)
  ├─ 同一事業の複数年度レコード
  ├─ 事業費（予算・決算）
  ├─ メタデータ（データ取込日時、ソース等）
  
jimu_jigyo_kpi_results (KPI指標)
  ├─ 活動指標・成果指標の結果
  ├─ 目標値・実績値・達成率を年度別に保存
  
jimu_jigyo_kpi_targets (KPI目標)
  ├─ 中期的な目標値管理（R7や最終年度目標）
```

### 3.2 詳細スキーマ

#### 📌 Table: `jimu_jigyo_items`
事務事業の基本情報。事業の識別子として機能。

```sql
CREATE TABLE jimu_jigyo_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  
  -- 事業識別
  item_code TEXT UNIQUE NOT NULL,  -- "somu_001" 等、自動採番
  item_name TEXT NOT NULL,         -- 事業名
  
  -- 所管情報
  bureau_code TEXT NOT NULL,       -- "somu", "fukushi", ... (11部局)
  bureau_name TEXT NOT NULL,       -- 総務企画局 等
  department_code TEXT NOT NULL,   -- 課コード
  department_name TEXT NOT NULL,   -- 課名
  
  -- 事業属性
  start_fiscal_year TEXT,          -- "平成23年度" 等
  root_law TEXT,                   -- 根拠法令
  administrative_plan TEXT,        -- 行政計画
  establishment_trigger TEXT,      -- 事業きっかけ
  
  -- 事業概要（長文、正規化も検討）
  target_description TEXT,         -- 対象の説明
  target_goal_state TEXT,          -- 対象の目指す状態
  implementation_content TEXT,     -- 実施内容
  achievement_criteria TEXT,       -- 成果見直し判断基準
  
  -- ロジックモデル
  activity_output TEXT,            -- 活動アウトプット
  result_output TEXT,              -- 結果アウトプット
  intermediate_outcome TEXT,       -- 中間アウトカム
  final_outcome TEXT,              -- 最終アウトカム
  
  -- メタデータ
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW(),
  
  CONSTRAINT bureau_code_valid CHECK (bureau_code IN (
    'somu', 'fukushi', 'hoken', 'kyouiku', 'kodomo',
    'juto', 'keizai', 'kankyo', 'shimin', 'nousui', 'kouwan'
  ))
);

CREATE INDEX idx_jimu_jigyo_items_item_name ON jimu_jigyo_items(item_name);
CREATE INDEX idx_jimu_jigyo_items_bureau_code ON jimu_jigyo_items(bureau_code);
```

#### 📌 Table: `jimu_jigyo_fiscal_years`
年度別のデータ。同一事業が複数年度存在。

```sql
CREATE TABLE jimu_jigyo_fiscal_years (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  
  -- 関連情報
  item_id UUID NOT NULL REFERENCES jimu_jigyo_items(id) ON DELETE CASCADE,
  fiscal_year INTEGER NOT NULL,         -- 令和6年=2024, 令和5年=2023, ...
  
  -- 予算情報（単位：千円）
  -- 支出額
  expenditure_amount INTEGER,           -- 決算見込・決算額
  expenditure_type TEXT,                -- "決算見込", "決算", "予算"
  specific_revenue INTEGER,             -- 特定財源
  general_revenue INTEGER,              -- 一般財源
  
  -- 次年度予算（参考）
  next_year_budget INTEGER,             -- 次年度予算
  
  -- データ品質・出所
  data_source TEXT,                     -- 福岡市HP、内部資料 等
  imported_at TIMESTAMP DEFAULT NOW(),  -- データ取込日時
  imported_by TEXT,                     -- 取込者/取込方法 (スクレイプ等)
  
  -- メタデータ
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW(),
  
  -- 一意性制約：同一事業の同一年度は1レコードのみ
  UNIQUE(item_id, fiscal_year),
  
  CONSTRAINT fiscal_year_valid CHECK (fiscal_year >= 2020 AND fiscal_year <= 2030)
);

CREATE INDEX idx_jimu_jigyo_fy_item_id ON jimu_jigyo_fiscal_years(item_id);
CREATE INDEX idx_jimu_jigyo_fy_fiscal_year ON jimu_jigyo_fiscal_years(fiscal_year);
```

### 3.3 基本計画・行政運営プランの扱い

現在のJSON では `基本計画` と `行政運営プラン` が格納されていますが、これらは事業が複数年度に渡って共通である可能性が高い。

**設計案：**
- 年度別に重複するデータなので、`jimu_jigyo_items` に統合格納、または
- 変更があれば `jimu_jigyo_fiscal_years` で上書きスキーム

→ **初期段階では `jimu_jigyo_fiscal_years` の JSON フィールドで柔軟に対応**

```sql
ALTER TABLE jimu_jigyo_fiscal_years ADD COLUMN
  basic_plan_data JSONB,               -- 基本計画情報
  administrative_plan_data JSONB;      -- 行政運営プラン情報
```

## 4. データ取込戦略

### 4.1 段階的な取込フロー

```
段階1: 令和6年度（✓ 完了）
  └─ 既存JSONから DB への一括取込

段階2: 令和5年度
  └─ JSONの R5 セクションから抽出・取込
  └─ R6と照合して既存item_idに紐付け

段階3: 令和4年度
  ├─ R4データのスクレイピング/PDF解析
  ├─ R3/R5との照合で事業追跡
  └─ 新規事業の検出

段階4: 令和3年度
段階5: 令和2年度
```

### 4.2 事業マッチング戦略（年度間の紐付け）

**課題**: 事業名の微妙な変更や異表記により、同一事業が別レコードとされる。

**マッチングロジック** (優先度順)：

1. **完全一致マッチング**
   ```sql
   WHERE item_name = ? AND bureau_code = ? AND department_code = ?
   ```

2. **部分一致 + 所管局一致**（事業名の改称対応）
   ```sql
   WHERE item_name LIKE '%' || ? || '%' 
     AND bureau_code = ?
     AND fiscal_year IN (current_year - 1, current_year)
   ```

3. **類似度スコアリング**（Levenshtein距離等）
   ```sql
   SELECT * FROM jimu_jigyo_items
   WHERE bureau_code = ?
   ORDER BY similarity(item_name, ?) DESC
   LIMIT 5
   ```
   → **手動確認リストとして提示**

4. **管理者による明示的なマッピング**
   - マッチング確信度が低い場合は管理画面で確認・修正

### 4.3 データ取込パイプライン（提案実装例）

```typescript
// packages/seed/jimu-jigyo-import/import-multi-year.ts

interface ImportTask {
  fiscalYear: number;              // 令和=西暦-18 (R6=2024)
  sourceType: 'json' | 'scrape' | 'pdf';
  sourceUrl?: string;
  jsonPath?: string;
}

async function importJimuJigyoData(task: ImportTask) {
  // 1. ソースデータ取得
  const rawData = await fetchSourceData(task);
  
  // 2. データ正規化
  const normalized = normalizeJimuJigyoData(rawData, task.fiscalYear);
  
  // 3. 既存事業とのマッチング
  for (const item of normalized) {
    const existingItem = await matchJimuJigyoItem(
      item.item_name,
      item.bureau_code,
      item.department_code
    );
    
    if (existingItem) {
      // 既存の item_id を再利用
      item.item_id = existingItem.id;
    } else {
      // 新規事業として作成
      item.item_id = await createJimuJigyoItem(item);
    }
  }
  
  // 4. DB への挿入（トランザクション）
  await insertJimuJigyoData(normalized, task);
  
  // 5. 検証・レポート
  await validateImport(task, normalized);
}
```

## 5. APIおよびクエリ設計

### 5.1 主要なクエリ例

#### 🔍 Q1. 同一事業の複数年度推移を取得

```sql
-- 「ユニバーサル都市・福岡の推進」の5年間の予算推移
SELECT
  fy.fiscal_year,
  fy.expenditure_amount,
  fy.specific_revenue,
  fy.general_revenue,
  ((fy.expenditure_amount - LAG(fy.expenditure_amount)
    OVER (ORDER BY fy.fiscal_year)) 
   / LAG(fy.expenditure_amount) 
    OVER (ORDER BY fy.fiscal_year) * 100)::INT AS change_rate_percent
FROM jimu_jigyo_items jj
JOIN jimu_jigyo_fiscal_years fy ON jj.id = fy.item_id
WHERE jj.item_name = 'ユニバーサル都市・福岡の推進'
  AND jj.bureau_code = 'somu'
ORDER BY fy.fiscal_year;
```

#### 🔍 Q2. 全部局の指標達成率の推移

```sql
-- 全成果指標の平均達成率を年度別に集計
SELECT
  fy.fiscal_year,
  COUNT(DISTINCT jj.id) AS item_count,
  AVG(
    CASE
      WHEN kr.achievement_rate ~ '^\d+(\.\d+)?%?$'
      THEN (kr.achievement_rate::numeric)
      ELSE NULL
    END
  ) AS avg_achievement_rate
FROM jimu_jigyo_fiscal_years fy
JOIN jimu_jigyo_items jj ON fy.item_id = jj.id
JOIN jimu_jigyo_kpi_results kr 
  ON EXISTS (
    SELECT 1 FROM jimu_jigyo_kpi_items ki
    WHERE ki.item_id = jj.id AND ki.id = kr.kpi_item_id
      AND ki.kpi_type_id = (
        SELECT id FROM jimu_jigyo_kpi_types WHERE kpi_type_code = 'achievement'
      )
  )
GROUP BY fy.fiscal_year
ORDER BY fy.fiscal_year DESC;
```

#### 🔍 Q3. 特定部局の予算削減事業の抽出

```sql
-- 令和5年→令和6年で予算が削減された事業
SELECT
  jj.item_name,
  r5.expenditure_amount AS r5_budget,
  r6.expenditure_amount AS r6_budget,
  (r6.expenditure_amount - r5.expenditure_amount) AS budget_change,
  ROUND(
    ((r6.expenditure_amount - r5.expenditure_amount) 
     / r5.expenditure_amount * 100)::numeric, 1
  ) AS change_rate_percent
FROM jimu_jigyo_items jj
JOIN jimu_jigyo_fiscal_years r5 ON jj.id = r5.item_id AND r5.fiscal_year = 2023
JOIN jimu_jigyo_fiscal_years r6 ON jj.id = r6.item_id AND r6.fiscal_year = 2024
WHERE jj.bureau_code = ?  -- 特定部局
  AND r6.expenditure_amount < r5.expenditure_amount
ORDER BY budget_change;
```

#### 🔍 Q4. 検索・フィルタリング

```sql
-- キーワード検索 + 部局絞込
SELECT DISTINCT
  jj.id,
  jj.item_name,
  jj.bureau_name,
  jj.department_name,
  COUNT(DISTINCT fy.fiscal_year) AS available_years
FROM jimu_jigyo_items jj
LEFT JOIN jimu_jigyo_fiscal_years fy ON jj.id = fy.item_id
WHERE (
  jj.item_name ILIKE ? 
  OR jj.implementation_content ILIKE ?
  OR jj.target_goal_state ILIKE ?
)
  AND (? IS NULL OR jj.bureau_code = ?)
GROUP BY jj.id, jj.item_name, jj.bureau_name, jj.department_name
ORDER BY jj.item_name;
```

## 7. リスク・制約

### 7.1 リスク

| リスク | 影響度 | 対策 |
|--------|--------|------|
| 過年度データのスクレイピング失敗 | 高 | 福岡市に直接確認・内部資料から手動入力 |
| 事業名の年度別変更による認識誤り | 中 | マッチングスコアリングと手動確認リスト |
| データ品質の不統一（R2～R6 の記載形式差異） | 中 | 正規化パイプライン・検証スクリプト |
| パフォーマンス低下（複数年度・全部局の大規模クエリ） | 中 | インデックス設計・キャッシング戦略 |

### 7.2 制約

- **R2～R4 の公開データ可用性**: 福岡市 HP に歴年データが保存されていない場合、取得困難
- **データ形式の変更**: 行政内部のシステム更新に伴い、将来のデータ形式が変わる可能性
- **年度定義**: 福岡市は 4 月～3 月の会計年度（令和 6 年度 = 2024 年 4 月～2025 年 3 月）を採用

## 8. まとめ

この設計により、以下が実現されます：

✅ **複数年度の統合管理**: R2～R6 の 5 年間のデータを関連付けて管理  
✅ **推移分析**: 同一事業の予算・KPI の5年推移を可視化  
✅ **全部局横断検索**: キーワード・部局・指標で効率的に検索  
✅ **スケーラビリティ**: 新年度の追加取込が容易  
✅ **監査可能性**: データ取込日時・ソース・変更履歴を記録
